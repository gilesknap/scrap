Deploy on Kubernetes#

Run scrap on a Kubernetes cluster (k3s, a home lab, a cloud cluster) with the Helm chart in charts/scrap. It runs the same container image as the single-server deployment: one pod, with the database on the node’s own disk and Litestream copying each change to a persistent volume, and nightly backups onto a second volume. For a first install, follow the tutorial Install scrap on Kubernetes; this page has every option.

How the pieces fit (one pod; the backup CronJobs run beside it on the same node). This example comes in through the Tailscale operator:

        flowchart LR
    phone["Phone and laptops<br/>(tailnet)"]:::user
    cc["Claude Code"]:::claude
    subgraph cluster ["Kubernetes cluster"]
        ts["Tailscale operator<br/>proxy"]
        ing["Ingress / Service"]
        subgraph node ["One node"]
            pod["scrap pod (1 replica):<br/>scrap, jobs (gc, related,<br/>topics), litestream"]
            db[("database<br/>emptyDir /db")]:::store
            data[("data PVC<br/>/data")]:::store
            jobs["CronJobs:<br/>backup, monthly backup"]
            bak[("backups PVC<br/>/backups")]:::store
        end
    end
    api["api.anthropic.com"]:::claude
    phone --> ts --> ing --> pod
    cc -->|"/mcp"| ts
    pod --- db
    pod --- data
    db -.->|"Litestream"| data
    jobs --- data
    jobs --> bak
    pod -.->|"ingest on"| api

Warning

scrap has no login of its own. Anyone who can reach its Service can read and change everything. Expose it only behind a login (Cloudflare Access, as in the tutorial, or an authenticating proxy: Any other ingress controller) or on your tailnet (Tailscale Kubernetes operator), never directly to the internet. Inside the cluster, any pod that can reach the Service has full access too, and can send its own Tailscale-User-Login header: turn on the NetworkPolicy (below) if other workloads share the cluster.

Prerequisites#

  • Kubernetes 1.29 or newer (Litestream runs as a native sidecar), and Helm 3 or 4.

  • A StorageClass that provides ReadWriteOnce volumes, and a few GB of free disk on the nodes. The database runs with Litestream, on the node’s disk, so the data volume may be a network filesystem such as NFS (k3s and storage notes).

  • A way in that is not the open internet: a Cloudflare Tunnel with Cloudflare Access (the tutorial’s route), the Tailscale Kubernetes operator for a tailnet, or an ingress controller behind a login proxy (Any other ingress controller).

  • For ingest: a Claude API key.

Get the image#

Releases publish a public, multi-arch (amd64 and arm64) image to ghcr.io/gilesknap/scrap, and the chart’s appVersion names the release it was made with (set from the git tag when the chart is published; a checkout has the placeholder 0.0.0, so set image.tag with one). By default the chart runs that release, ghcr.io/gilesknap/scrap:<appVersion>, so there is nothing to build: set image.tag only to run a different release.

To run your own build instead, push it to a registry your cluster can pull from, and point the chart at it:

podman build --platform linux/amd64,linux/arm64 --manifest registry.example.com/scrap:dev .
podman login registry.example.com
podman manifest push registry.example.com/scrap:dev

image:
  repository: registry.example.com/scrap
  tag: dev
  pullPolicy: Always
imagePullSecrets:
  - name: my-registry-credentials   # if the registry needs a login

Building the arm64 half on an x86 machine needs qemu-user-static; on a mixed cluster you can instead pin scrap to nodes of one architecture with nodeSelector: {kubernetes.io/arch: amd64} and build only that.

Install#

A minimal my-values.yaml, here with the Tailscale operator for access and ingest on (for Cloudflare, the tutorial’s values). It runs the release image the chart names, and assumes the Secret from Secrets and ingest; add an image block as above to run your own build, and drop ingest to run without Claude:

ingest:
  enabled: true
  existingSecret: scrap-secrets
ingress:
  enabled: true
  className: tailscale
  tls:
    - hosts: [scrap]
litestream:
  enabled: true

litestream.enabled is the default from chart 1.9.0; set it anyway, so the values work with any chart from 1.7.0.

From the released chart (version = the release tag, with a pre-release 0.4.0rc1 as 0.4.0-rc.1):

kubectl create namespace scrap
helm install scrap oci://ghcr.io/gilesknap/charts/scrap --version <release> --namespace scrap -f my-values.yaml
kubectl -n scrap rollout status deploy/scrap

The commands in this guide assume the release is called scrap in the namespace scrap. For another name, use the chart’s fullname instead (kubectl -n scrap get deploy,cronjob,pvc lists the names, and helm install prints them in its notes).

Check it without exposing it anywhere:

kubectl -n scrap port-forward svc/scrap 8000:80
curl http://127.0.0.1:8000/healthz

and open http://127.0.0.1:8000/ for the PWA. The PWA needs HTTPS to install on a phone (see Capture from your phone (the PWA)), so use one of the exposures below for that.

Leave service.type at ClusterIP: the chart assumes access goes through the Ingress or a port-forward. LoadBalancer and NodePort open the Service to whatever network the node or load balancer is on, and scrap has no login, so use them only on a private network. With ingress.hosts empty, the Ingress has one rule that matches any host (the Tailscale example below relies on this); with hosts set, each gets its own host-specific rule. The charts/scrap/ci directory holds the value sets the chart is tested with (defaults, no backup, existing claims, a generic ingress, ingest, long names, and the Tailscale Ingress and Service), which are worked examples to copy from.

The settings themselves are in the API reference. The chart sets SCRAP_DATA_DIR=/data and SCRAP_DB_PATH=/db/scrap.db; SCRAP_WEB_DIR (for trying out a PWA build) has no value of its own, use extraEnv.

Set TZ the same way, to your own time zone: the server decides what “today” means for due:today searches from its own clock (UTC by default), while the PWA uses the phone’s date.

extraEnv:
  - name: TZ
    value: Europe/London

The preview cache (cache/previews under /data) stays on the data volume: it is regenerable and never backed up, and keeping it saves redoing every preview after a restart, which is slow on small ARM nodes.

Secrets and ingest#

The chart never takes the API key as a value and never creates a Secret: it only reads a Secret you create. Create it from a file or stdin so the key stays out of your shell history and out of any values file:

read -rs KEY && printf %s "$KEY" | kubectl -n scrap create secret generic scrap-secrets \
    --from-file=ANTHROPIC_API_KEY=/dev/stdin; unset KEY

Optionally add the notification URL (an ntfy topic URL is itself a secret) to the same Secret under another key, e.g. SCRAP_NOTIFY_URL. Then:

ingest:
  enabled: true
  existingSecret: scrap-secrets
  apiKeyKey: ANTHROPIC_API_KEY     # the default
  notifyUrlKey: SCRAP_NOTIFY_URL   # optional

With ingest on, Claude also tags, summarises and links text pages and fetches the links you save (SCRAP_ENRICH, on by default). That shares the daily budget with photos (ingest.budgetDayUSD, $3 per UTC day by default), and the pod then makes outbound HTTP and HTTPS requests (ports 80 and 443) to public sites. To keep Claude to photos, switch it off:

extraEnv:
  - name: SCRAP_ENRICH
    value: "off"

With enrich on, a page made from a PDF or text file also has the start of its text (at most 4,000 characters, never the file) sent to Claude once it is read, for a title, tags and a summary (ADR 38). To keep file text on the host unless you press Ask Claude, set SCRAP_FILE_ENRICH to ask:

extraEnv:
  - name: SCRAP_FILE_ENRICH
    value: "ask"

With GitOps, create the Secret with whatever your cluster uses for secrets (Sealed Secrets, External Secrets, SOPS) under the same name; never commit the key. A changed Secret is not picked up by a running pod: kubectl -n scrap rollout restart deploy/scrap.

Exposure#

Pick one way in. None of them opens scrap to the internet without a login.

Cloudflare Tunnel and Access#

A cloudflared Deployment carries an outbound tunnel straight to scrap’s Service, with Cloudflare Access in front: an email one-time PIN for the web app and a service token for /mcp, behind scrap’s own bearer token. The cluster opens no port and needs no ingress controller. Install scrap on Kubernetes walks through it, values included.

Tailscale Kubernetes operator#

With the Tailscale Kubernetes operator installed, an Ingress of class tailscale publishes scrap over HTTPS on your tailnet only, with a MagicDNS name and a Let’s Encrypt certificate (cluster ingress, L7 ingress how-to). Your tailnet needs MagicDNS and HTTPS certificates enabled.

ingress:
  enabled: true
  className: tailscale
  tls:
    - hosts:
        - scrap          # becomes https://scrap.<tailnet>.ts.net

The operator’s proxy accepts traffic through Tailscale Serve (architecture). Never add the Funnel annotation: that publishes scrap to the internet.

The alternative, the Service annotation tailscale.com/expose: "true" (with tailscale.com/hostname), forwards plain TCP: there is no HTTPS, so the PWA cannot install or work offline, and there are no identity headers. Use the Ingress.

Identity headers. scrap records the Tailscale-User-Login header as the author of each change. Tailscale Serve sets it, and strips any value the client sent, for requests from user-owned devices, and sets none for tagged devices. The operator’s documentation does not say whether its Ingress proxy does the same. Its proxy configures Serve through the same local API, and in Tailscale’s source the Serve reverse proxy adds the headers to every proxied request (ipn/ipnlocal/serve.go, addTailscaleIdentityHeaders), so they are expected to arrive, but this is not yet verified end to end. To check on your cluster: make a change from a phone or laptop through the Ingress, then look at the page’s history (or GET /api/pages/<id>): your tailnet login should be its author, not the fixed fallback author tagged. If it is not, every change is recorded as tagged; nothing else breaks.

The chart leaves networkPolicy off and /mcp without a token by default; see MCP server and access for the values to set on a shared cluster.

Because a pod inside the cluster can send its own Tailscale-User-Login header straight to the Service, let only the operator’s proxies in (they run in the operator’s namespace, tailscale by default):

networkPolicy:
  enabled: true
  from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: tailscale

A NetworkPolicy needs a CNI that enforces it (k3s’s built-in controller does). Check that the policy exists (kubectl -n scrap get networkpolicy): a misspelt key inside networkPolicy is not rejected. Whether kubelet probes still get through depends on the CNI; if the pod never becomes ready after turning the policy on, check that first.

Tailnet ACL: deny tagged devices by default#

The operator’s proxies are tagged devices (tag:k8s by default). As for the single server, use a tailnet policy that lets your own devices reach them and gives other tagged devices (servers, CI, anything unattended) no access unless you grant it:

"grants": [
  {"src": ["autogroup:member"], "dst": ["tag:k8s"], "ip": ["tcp:443"]}
]

Any other ingress controller#

scrap has no login, so put an authenticating proxy in front: for example oauth2-proxy through your controller’s external auth annotations, or your SSO’s forward-auth middleware. Raise the controller’s request body limit a little above maxUploadMB, so an upload just over it gets scrap’s error rather than the controller’s.

ingress:
  enabled: true
  className: <your-ingress-class>
  annotations:
    # Your controller's annotations for external authentication and for a
    # request body limit a little above maxUploadMB; see its documentation.
    <auth-annotation>: <auth-service-url>
    <body-size-annotation>: 51m
  hosts:
    - scrap.example.com
  tls:
    - hosts:
        - scrap.example.com
      secretName: scrap-tls

The annotation names differ for every controller (Traefik uses Middleware objects instead), so the chart takes them as plain ingress.annotations. Make sure the proxy removes any Tailscale-User-* headers sent by clients; changes are then recorded under the fixed fallback author tagged. Never expose the Service without authentication.

The Ingress sends every path to scrap, so the proxy covers /mcp and /healthz too. /mcp is called by Claude Code, not a browser, so a login page in front of it will block it unless the proxy exempts that path or the client can pass its check; the tailnet route avoids the problem.

Behind oauth2-proxy. Set identityHeader: X-Auth-Request-User (the header oauth2-proxy returns and the controller copies to the request), so the author is the real login. scrap trusts only that header, but most controllers do not strip a client-sent copy, so the proxy plus the NetworkPolicy must be the only way to the Service; a forged value only changes the recorded author.

Exposing /mcp (Cloudflare Access, a second ingress). For a complete walk-through with a Cloudflare Tunnel straight to the Service, see Install scrap on Kubernetes. With an ingress controller, give /mcp its own Ingress rule or host that skips the login proxy, and guard it another way: a Cloudflare Access service token in front, and scrap’s own bearer token behind it (below), so a leaked service token alone does not open scrap. Keep the PWA and API on the login-proxied host.

A central oauth2-proxy with ingress-nginx#

If you run oauth2-proxy in the cluster (with reverse_proxy and set_xauthrequest on, and no fixed redirect_url), the chart wires it in:

authProxy:
  enabled: true
  service: oauth2-proxy.scrap.svc.cluster.local   # the proxy's in-cluster DNS name
  allowedUsers: [abc12345]                            # who may use the web app (usernames)
  oidc:
    issuer: https://identity.example.org/realms/main  # the realm, as in its tokens' iss
    clientId: scrap                                   # the proxy's client

The Ingress then gets ingress-nginx’s auth-url (the proxy’s /oauth2/auth, with no allowed_emails query, which some ingress-nginx annotation validation refuses), auth-signin and auth-response-headers: X-Auth-Request-Email,X-Auth-Request-Access-Token annotations, on top of ingress.annotations. A second Ingress, <fullname>-open, with the same class, hosts and tls and no auth, sends /mcp to scrap (set mcp.tokenSecret) and /oauth2 to the proxy through an ExternalName Service, so the sign-in, its callback (https://<host>/oauth2/callback, which the identity provider must allow) and the cookie are on scrap’s own host. Both Ingresses get proxy-buffer-size: 16k unless ingress.annotations sets it, since the login’s cookies overflow nginx’s 4k default. The author of a change is the username (preferred_username) in the proxy’s token, so identityHeader is not read. The install fails without ingress.enabled, ingress.tls (the cookie is https only), mcp.tokenSecret.name, authProxy.service, authProxy.allowedUsers, authProxy.oidc.issuer or authProxy.oidc.clientId.

The login alone guards the Ingress only: without a NetworkPolicy, any pod can reach the Service and send its own X-Auth-Request-Email. So scrap checks the proxy’s access token itself (ADR 45): the Deployment gets SCRAP_OIDC_ISSUER, SCRAP_OIDC_CLIENT_ID and SCRAP_ALLOWED_USERS, and every request but /healthz and /mcp needs a valid token for an allowed username (401 without). This is also the only owner check: anyone the proxy lets log in passes the Ingress. Run the proxy with pass_access_token = true, and a cookie_refresh shorter than the access tokens’ life. Other controllers need their own annotations, above. DLS runs one proxy for every user this way: Run the DLS login proxy.

Bearer token on /mcp#

Create the Secret yourself (the chart never takes a token as a value) and name it:

mcp:
  tokenSecret:
    name: scrap-secrets      # may be the Secret that holds ANTHROPIC_API_KEY
    key: SCRAP_MCP_TOKEN     # one token, or several comma separated to rotate

Generate one with python -c 'import secrets; print(secrets.token_urlsafe(32))'. To rotate, set the key to old,new, roll the pod, move the clients to new, then drop old. /healthz stays open for the probes. Clients send Authorization: Bearer <token>: see Connect a Claude Code session.

Claude Code (MCP)#

Claude Code sessions talk to scrap’s /mcp endpoint (see Connect a Claude Code session and MCP server). It answers 421 to any Host that is not loopback or listed in SCRAP_PUBLIC_URL, and the chart has no value for it, so set it through extraEnv to the address you reach scrap at:

extraEnv:
  - name: SCRAP_PUBLIC_URL
    value: https://scrap.<tailnet>.ts.net

The same address makes the page links the MCP tools return absolute.

Warning

The web app and API check Host as well: a hostname missing from SCRAP_PUBLIC_URL gets 421 on every page, not just /mcp. Set it to the address you reach scrap at (/healthz, which the probes use, answers to any name), and roll the pod after changing it.

Port-forward#

For a quick try, kubectl -n scrap port-forward svc/scrap 8000:80. Nothing is exposed beyond your own machine.

Public pages#

scrap can publish the pages you mark Public to a static site on the internet, for example https://pages.example.org. The site is served by nginx from a separate image, ghcr.io/gilesknap/scrap-public, which also holds a small upload receiver. scrap pushes each public page to the receiver; nothing on the public side can reach scrap. Making pages public in the app is in Publish pages. The contract between the two sides (the receiver’s API, what each unit may hold, nginx’s paths and headers) is Public site, and why it is built this way is ADR 43. The chart’s public section, off by default, runs it:

  • it runs in a namespace of its own (public.namespace, default scrap-public), labelled Pod Security restricted, which you create first (below);

  • one Deployment with two containers sharing the site volume: web (nginx, the site mounted read only) and receiver (the only one given the token, mounted as a file), both non-root with read-only root filesystems;

  • two ClusterIP Services, and an Ingress for nginx alone (public.ingress); the receiver is never on an Ingress;

  • a NetworkPolicy: the receiver’s port only from scrap’s pods (the release namespace and scrap’s labels), nginx’s port from public.networkPolicy.webFrom (empty: anyone, as nginx serves only public files; set it to your ingress controller’s namespace to narrow it), and no egress at all.

The site lives in an emptyDir (public.sizeLimit, default 3Gi: the receiver’s 2 GiB quota plus room for an upload). It starts empty when the pod moves, and scrap fills it again: it checks the receiver’s manifest at start and every 10 minutes and pushes what is missing.

First create the public namespace, labelled Pod Security restricted, and the upload token. The token is a Secret you create, never a value. The receiver runs in the public namespace and scrap in its own, and a pod reads only its own namespace’s Secrets, so create it, with the same name and key, in both:

kubectl create namespace scrap-public
kubectl label namespace scrap-public pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=restricted pod-security.kubernetes.io/warn=restricted
token=$(openssl rand -hex 32)
for ns in scrap scrap-public; do
  kubectl -n "$ns" create secret generic scrap-publish --from-literal=token="$token"
done

Both pods read the token as a mounted file, never an environment variable: the receiver through RECEIVER_TOKEN_FILE, scrap through SCRAP_PUBLISH_TOKEN_FILE.

public.createNamespace: true makes the chart create the namespace instead, with the same labels. Argo CD’s CreateNamespace=true does not do it: that creates only the Application’s destination namespace (scrap’s), so scrap-public must exist first or come from public.createNamespace. With the chart creating it, the Secret can only be made after the first install, and the receiver waits for it. helm uninstall (or an Argo CD prune) then deletes the namespace, and the Secret in it, which is why it is off by default.

Then:

public:
  enabled: true
  site: https://pages.example.org     # SCRAP_PUBLISH_SITE
  tokenSecret:

Behind Cloudflare Access: if your domain has a wildcard Access application (*.example.org), it covers every subdomain, the public site’s too, and visitors meet a login. Cloudflare’s browser cache: a zone’s Browser Cache TTL (4 hours by default) rewrites the site’s Cache-Control: no-cache on /assets/*.css and *.js to max-age=14400, so readers see last release’s stylesheet (#534). Add a Cache Rule for the site’s host with Browser TTL: Respect origin TTL, then check: curl -sI https://pages.example.org/assets/page.css shows cache-control: no-cache.

Upgrades#

Back up first, then upgrade to the newer chart version (its image follows, unless your values set image.tag: change that too).

kubectl -n scrap create job --from=cronjob/scrap-backup scrap-backup-pre-upgrade
kubectl -n scrap wait --for=condition=complete job/scrap-backup-pre-upgrade --timeout=30m
helm upgrade scrap oci://ghcr.io/gilesknap/charts/scrap --version <new> -n scrap -f my-values.yaml

From a checkout, helm upgrade scrap ./charts/scrap -n scrap -f my-values.yaml --set image.tag=<new> instead.

The old pod stops before the new one starts (Recreate), so there is a short outage; the PWA queues captures meanwhile. A clean stop gives any ingest job in flight back to the queue. scrap runs its database migrations at startup, before it answers /healthz: the startup probe allows them five minutes.

Migrations are forward only, and an older scrap refuses a database migrated by a newer one. So helm rollback alone does not go back: you also restore the pre-upgrade backup. This works only back to a release that ran Litestream (1.7.0 or newer); to go back from an upgrade out of the old mode, see Upgrading from the old mode.

  1. Follow the restore steps under Backup and restore with the pre-upgrade backup and the old image, up to and including kubectl -n scrap delete pod scrap-restore. Leave scrap at 0.

  2. Choose the revision to go back to. List them, then check that revision’s images (its APP VERSION can mislead when image.tag is pinned):

    helm -n scrap history scrap
helm -n scrap get manifest scrap --revision <N> | grep image:

    Every scrap image must be the old one. Then roll back to that revision:

    helm -n scrap rollback scrap <N>

  3. Confirm that the Deployment names the old image, for scrap, jobs and db-init:

    kubectl -n scrap get deploy/scrap -o jsonpath='{range .spec.template.spec.initContainers[*]}{.name}={.image}{"\n"}{end}{range .spec.template.spec.containers[*]}{.name}={.image}{"\n"}{end}'

    scrap must start on the old image, or it migrates the staged backup forward again. If this shows the new image and a pod has started, scale to 0 at once (kubectl -n scrap scale deploy/scrap --replicas=0), stage the restore again (step 1) and pick the revision again.

  4. Start it, and resume the backups:

    kubectl -n scrap scale deploy/scrap --replicas=1
kubectl -n scrap patch cronjob scrap-backup -p '{"spec":{"suspend":false}}'

    The rollback may already have set one replica; the scale is then harmless.

With Argo CD, the sync starts the pod, so check the image before you sync. In place of step 2, set targetRevision back to the old chart version, keeping litestream.enabled: true in the values, and confirm the image that version runs: its appVersion (helm show chart oci://ghcr.io/gilesknap/charts/scrap --version <old>), or your image.tag if you pin one. Then sync, do steps 3 and 4 at once, and turn automatic sync back on.

Anything captured since the upgrade is then lost from the database; its files stay. Never roll back to a chart before 1.7.0 (The database on an emptyDir, with Litestream).

Upgrading from the old mode#

This applies when you upgrade to chart 1.9.0 or later from an install that never set litestream.enabled. Such an install has its database at /data/scrap.db, and gc and the Claude passes as CronJobs. The first helm upgrade to 1.9.0 or later moves it across (why: ADR 47):

  • The CronJobs scrap-gc, scrap-enrich-related and scrap-enrich-topics become suspended stubs of the same names, which run nothing, with helm or Argo CD (pruning or not). Their work moves to the pod’s jobs container. Suspending stops new runs, not a Job already running.

  • In the new pod, db-init copies /data/scrap.db (with its WAL) to /db/scrap.db, checks it, and writes a state file. It refuses, starting nothing, if the database and its WAL are over half of litestream.sizeLimit.

  • Litestream makes the replica in /data/litestream within about a second; then scrap and jobs start. /data/scrap.db stays where it was, as the copy from before, and must not change: if anything writes to it, the next start stops in db-init.

The steps:

  1. Check Kubernetes is 1.29 or newer: kubectl version.

  2. Check the values. No @every or signed numbers in gc.schedule, enrichRelated.schedule or enrichTopics.schedule; room in any ResourceQuota or LimitRange for the bigger pod; with backup.persistence.hostPath, a namespace that allows hostPath volumes.

  3. Check the database’s size. kubectl -n scrap exec deploy/scrap -- ls -l /data/scrap.db /data/scrap.db-wal (there may be no -wal). Together they must be at most half of litestream.sizeLimit: 1 GiB at the default 2Gi. If not, raise litestream.sizeLimit to over twice that, on nodes with that much free disk.

  4. Back up, and wait for it:

    kubectl -n scrap create job --from=cronjob/scrap-backup scrap-backup-pre-litestream
kubectl -n scrap wait --for=condition=complete job/scrap-backup-pre-litestream --timeout=30m

  5. Pick a quiet moment: make sure no gc or enrich Job is still running before you upgrade (suspending stops new runs, not a running one): kubectl -n scrap get jobs shows none running. By default they start between 03:30 and 04:30, and the related pass can run for hours. A Job still writing /data/scrap.db after the copy stops the next start.

  6. Upgrade: helm upgrade as above, or an Argo CD sync. Then check that the three old CronJobs are suspended:

    kubectl -n scrap get cronjob scrap-gc scrap-enrich-related scrap-enrich-topics

    Each shows SUSPEND True. Delete any that does not (a later sync recreates it suspended): an old one left running keeps its old image, and from a chart of 1.6.0 or older its gc deletes the files only the new database uses.

  7. Check. kubectl -n scrap logs deploy/scrap -c db-init says it brought /data/scrap.db across to /db/scrap.db; kubectl -n scrap exec deploy/scrap -c jobs -- scrap schedule status lists the jobs; and a backup completes: kubectl -n scrap create job --from=cronjob/scrap-backup scrap-backup-post-litestream.

  8. Later, once you are happy, delete /data/scrap.db, and any /data/scrap.db-wal and /data/scrap.db-shm, from the jobs container.

If the pod dies in the second between the copy and Litestream’s first write, the next start refuses (a state file but no replica): look, then set litestream.init.override: true for one start.

helm rollback to the release before this upgrade is no way back: scrap refuses to start on the old file while the state file is there, and with ingest on the old Claude-pass CronJobs come back and write to it. The way back is a backup and a restore. To stay on the old mode for now, set litestream.enabled: false before upgrading; it is deprecated. helm upgrade --reuse-values from a 1.7 or 1.8 release does the same without being asked: it reuses the old chart’s enabled: false, and the install notes say DEPRECATED.

Backup and restore#

The daily CronJob runs scrap backup into a new timestamped directory on the backup claim (/backups/20261019T033000Z), then keeps only the newest backup.keep runs, using the same rules as the single-server deployment: keep must be a whole number of at least 1 (the chart refuses anything else), and only real directories named like a run are ever deleted; anything else on the volume, including symlinks, is left alone. A failed run removes only its own directory. scrap backup is safe while scrap is serving. The job runs on the same node as the scrap pod (pod affinity), because the data volume is ReadWriteOnce; while scrap is scaled to zero, a run waits and gives up after an hour. Runs never overlap, and one that cannot start within an hour of its schedule is skipped. A failed run is retried once and then counted as failed; the last 3 successful and the last 3 failed Jobs are kept, so kubectl logs still works on them.

Monthly copy. A second CronJob, <fullname>-backup-monthly (03:50 on the 1st), makes the same full backup into the monthly/ folder of the backup claim and keeps the newest backup.monthly.keep (12) there. It takes the same lock as the daily backup and gc, so they never overlap. The daily prune, gc’s recent-backup check and the restore commands below look only at runs directly in the claim, so none of them touches monthly/; to restore one, point restore at /backups/monthly/<run>. Switch it off with backup.monthly.enabled: false.

        flowchart LR
    d["daily CronJob<br/>03:30"] -->|"keep 7"| r[("/backups/<br/>YYYYMMDDTHHMMSSZ")]:::store
    m["monthly CronJob<br/>03:50 on the 1st"] -->|"keep 12"| mm[("/backups/monthly/<br/>YYYYMMDDTHHMMSSZ")]:::store
    g["gc, in the jobs container<br/>04:30"] -.->|"needs a COMPLETE run<br/>under 26 h old"| r
    classDef store fill:#e8f1ff,stroke:#4a7bd0

The daily CronJob is called <fullname>-backup, which is scrap-backup for the release used in this guide. When a CronJob’s name would be longer than 52 characters, the chart shortens the fullname and adds a 6-character hash, so the name differs: read it from kubectl -n scrap get cronjob and use it in place of scrap-backup in the commands below and under Upgrades.

Backups are on by default because the data is personal and irreplaceable; set backup.enabled: false if you back up the data volume another way (volume snapshots, Longhorn or Velero backups). Either way the backup claim lives in the same cluster: copy it somewhere else too.

Run one now and follow it:

kubectl -n scrap create job --from=cronjob/scrap-backup scrap-backup-now
kubectl -n scrap logs -f job/scrap-backup-now

To restore, stop scrap (and anything that would restart it), then stage the backup with scrap restore --stage in a one-off pod with both claims mounted. The next start of scrap takes it up:

kubectl -n scrap patch cronjob scrap-backup -p '{"spec":{"suspend":true}}'
kubectl -n scrap scale deploy/scrap --replicas=0
kubectl -n scrap wait --for=delete pod -l app.kubernetes.io/name=scrap --timeout=2m
kubectl -n scrap apply -f restore.yaml
kubectl -n scrap wait --for=jsonpath='{.status.phase}'=Succeeded pod/scrap-restore --timeout=10m
kubectl -n scrap delete pod scrap-restore
kubectl -n scrap scale deploy/scrap --replicas=1
kubectl -n scrap patch cronjob scrap-backup -p '{"spec":{"suspend":false}}'

The monthly CronJob needs no suspending: like the daily one, it waits for the scrap pod. With Argo CD or another GitOps controller, pause its automatic sync first, or it scales scrap straight back up. restore.yaml, with the run to restore and the image of the scrap version you want (the chart’s image.repository and tag of the release that wrote the backup, or a newer one: restore refuses a backup from a newer scrap, see Which backups restore):

apiVersion: v1
kind: Pod
metadata:
  name: scrap-restore
spec:
  restartPolicy: Never
  automountServiceAccountToken: false
  # imagePullSecrets: [{name: my-registry-credentials}]   # if the registry needs a login
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: restore
      image: ghcr.io/gilesknap/scrap:<version>
      args: ["restore", "/backups/<run>", "--stage", "--force"]
      env:
        - name: SCRAP_DATA_DIR
          value: /data
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: [ALL]
      volumeMounts:
        - {name: data, mountPath: /data}
        - {name: backups, mountPath: /backups, readOnly: true}
        - {name: tmp, mountPath: /tmp}
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: scrap-data
    - name: backups
      persistentVolumeClaim:
        claimName: scrap-backups
    - name: tmp
      emptyDir: {}

The claim names are <fullname>-data and <fullname>-backups, where the fullname is the release name if it contains scrap, else <release>-scrap: kubectl -n scrap get pvc shows them. scrap restore prints nothing when it works and exits non-zero with a message when it does not (kubectl -n scrap logs pod/scrap-restore; the wait above then times out instead of returning). It works on a copy and never writes to the backup, so the backups claim can be mounted readOnly: true, as above. The same pod with other arguments runs any scrap command against the data, for example ["export", "/backups/export"] (which does need the claim writable; pruning only ever deletes directories named like a backup run, so an export there is kept). To restore into a fresh volume instead, create a new claim, restore into it without --stage or --force, and point persistence.existingClaim at it. The new pod brings the database across on its first start and leaves /data/scrap.db in place: delete it later, as in step 8 of Upgrading from the old mode. A backup with no pages is not brought across, and if any backups or stored files exist (runs in the backup folder or its monthly/, or files in /data/files) the pod then refuses to start empty. Set litestream.init.override: true for one start if that is what you want, and set it back. gc then only counts until you run kubectl -n scrap exec deploy/scrap -c jobs -- scrap db-hold --clear: do that once things look right.

What --stage does. A plain restore over the database would be undone, because the next start restores the replica. --stage checks and migrates the backup and leaves it at /data/scrap.db.restored; --force is needed unless files/ is empty (files are only ever added). The next start takes it up in place of the replica, and renames the old replica /data/litestream.retired-<time>; Litestream starts a new one. Pages written since the backup are gone from the database. The retired replica holds their database rows, but you can only get them back by hand, restoring it to a scratch copy (litestream restore -o <file> file:///data/litestream.retired-<time>); it does not hold files. Files added since the backup are in files/, but nothing refers to them now, so gc would delete them: for 14 days after a restore gc only counts, to give you time to go through them. scrap db-hold --clear ends that sooner. See what happened with kubectl -n scrap logs deploy/scrap -c db-init, then make a backup. Once you are happy, delete the retired folder with the one-off pod (["sh", "-c", "rm -rf /data/litestream.retired-*"] with command: in place of args:), as it takes up room on the volume.

If you forget --stage the pod stops in Init, saying /data/scrap.db has changed: it will not choose between that file and the replica, either of which may be newer. Rename the file away to keep the replica, or to scrap.db.restored to keep the file and retire the replica. scrap restore in the running pod is refused, with or without --stage. If scrap is not scaled to 0 when you stage a restore from a one-off pod, it goes on taking writes, and nothing stops it: the restore waits for the next start. That start refuses if the pod has kept its database, or if the replica has anything newer than the staged file, and says how to choose: delete the staged file to keep those writes, or touch it with scrap at 0 to restore anyway.

Backups in a hostPath. With backup.persistence.hostPath, there is no backups claim. Mount the directory instead, and run the pod as the release’s podSecurityContext user, who owns the backups (the DLS install uses your own uid and gid; id shows them):

  securityContext:
    runAsNonRoot: true
    runAsUser: <uid>
    runAsGroup: <gid>
    fsGroup: <gid>
    seccompProfile:
      type: RuntimeDefault
  ...
  volumes:
    - name: backups
      hostPath:
        path: <the backup directory>
        type: Directory

Which backups restore#

What scrap restore accepts depends on the schema of the backup (the database version, named in the error message below) against the release that runs the restore:

The backup is

scrap restore

the same schema as the release

Copied as it is.

lower than the release’s schema (an older release made it)

Migrates: restore runs the numbered migration scripts after the backup’s version on its copy before the swap, so the data folder only ever receives a current database. A failed migration leaves the database as it was (files already copied stay, and are harmless).

above the release’s schema (a newer release made it)

Refuses: bad backup: <db> has schema N; this scrap knows M. Use the release that wrote the backup, or a newer one.

Pointing a newer server at an older store migrates it in place when it starts (scrap serve migrates before it answers /healthz), so an upgrade needs no restore. Migrations are one-way: once a newer server has migrated the live store, going back to the old image needs a restore of a backup taken before the upgrade (see Upgrades above), and backups taken after it are refused by the old image.

Try a restore in a scratch instance#

A backup you have never opened is a hope, not a backup. This checks one on any machine, with nothing touching the cluster’s data: restore it into a throwaway folder, start scrap on another port and compare what it shows with the live store.

Room. You need room for two copies of the store: the run you copy off the cluster and the restored folder. Check the size first with kubectl -n scrap exec deploy/scrap -- du -sh /db /data/files (about 500 MB free for a 250 MB store), and keep everything in one folder you can delete at the end. The steps call it $RT; pick a disk with room, not a small /tmp; it is created new, so the final rm -rf "$RT" removes nothing else.

export RT=$(mktemp -d "$HOME/rt.XXXXXX")   # a new, empty folder; put another disk's path in place of $HOME if needed
mkdir "$RT/backup"

import json, urllib.request

def get(port, path):
    with urllib.request.urlopen(f"http://localhost:{port}{path}") as r:
        return json.load(r)

def key(p):
    return [p.get("title"), p.get("body"), sorted(p.get("tags") or []), p.get("kind"),
            p.get("fields"), p.get("rev"), p.get("writeup")]

a, b = get(8793, "/api/pages?limit=500"), get(8794, "/api/pages?limit=500")
sa, sb = {p["slug"] for p in a}, {p["slug"] for p in b}
print(len(sa), "restored,", len(sb), "live; only restored:", sorted(sa - sb), "only live:", sorted(sb - sa))
bad = 0
for slug in sorted(sa & sb):
    if key(get(8793, f"/api/pages/{slug}")) != key(get(8794, f"/api/pages/{slug}")):
        bad += 1
        print("differs:", slug)
print(bad, "differ")
for port in (8793, 8794):
    todos = len(get(port, "/api/pages?kind=todo&limit=500"))
    trash = get(port, "/api/trash?limit=500")["total"]
    print(port, "todos:", todos, "trash:", trash)
PY

GET /healthz shows the version of the scratch instance, which is the scrap you ran in step 2, so it differs from the live version if you used another release. Same or newer than live is fine; older cannot read a newer backup and restore refuses it.

  • The backup holds the database and every file in files/. It does not hold cache/, the page previews, which scrap makes again the first time a photo is shown.

  • enrich.on and writeup.on read false on the scratch instance only because Claude is off there. A newer scrap can also count more in GET /api/health: the restored copy may report a check (is:outdated, for example) as nonzero that a live service on an older version does not run.

Health and monitoring#

/healthz answers 200 with the version while scrap is well. It answers 503 when ingest is on and its worker thread has died; the liveness probe then restarts the pod, which is intended (the readiness probe takes it out of the Service first). Logs: kubectl -n scrap logs deploy/scrap. Ingest pauses (budget spent, credit, auth) are reported once per episode to SCRAP_NOTIFY_URL if set, and are visible at GET /api/ingest. kubectl -n scrap exec deploy/scrap -c jobs -- scrap schedule status reports gc, the Claude passes and the newest backup, and exits 1 on a problem (Are the nightly jobs healthy?). The backup CronJob’s failed jobs stay listed (kubectl -n scrap get jobs); alert on them with whatever watches your cluster.

Scheduled gc, related pages and topics#

Besides the backup, the chart runs scrap gc nightly and, while ingest.enabled is true, the nightly related-pages pass and the weekly topics pass. They run in the scrap pod’s jobs container (scrap schedule), because they need the live database; Scheduled jobs lists each one’s schedule, what it does, whether it spends from the Claude budget and the values that set it. How they run, fail and are checked is in The database on an emptyDir, with Litestream.

gc deletes only if the backup claim holds a completed run (one with the COMPLETE file written once the backup passed an integrity check) less than 26 hours old; otherwise it only counts, and the run fails so a missing backup shows. It takes the backup’s lock (/backups/.lock), so it never runs during a backup; so gc.enabled follows backup.enabled unless set, and gc.enabled: true with backups off is refused (unless gc.requireBackup: false). If you back up another way, set gc.requireBackup: false. A deleting scrap gc also takes a lock of its own (gc.lock in the data folder), so one you run by hand cannot overlap the scheduled one: whichever starts second stops with another scrap gc is deleting; a hand run does not wait for a backup. With ingest.notifyUrlKey set, gc pushes to SCRAP_NOTIFY_URL when it starts a month’s Orphaned assets page.

Its deletes are permanent: files nothing refers to (no page’s text, trashed pages included, no capture, no derived result, no job, no model run) and older than graceHours; the stored prompts and raw responses of Claude calls older than runDays that nothing refers to; the pages in the trash for more than trashDays (default 30), topic pages aside, with their captures, history and Claude’s results, whose files then go as unused ones; and finished job records older than jobDays (default 30). It never deletes a page, or its captures and files, before then (see Scheduled jobs, and the PWA’s Trash: The trash). The scrap pod shows each trashed page’s purge date from trashDays (SCRAP_TRASH_DAYS, off while the job does not delete). Set gc.delete: false to have it only count until you trust it. To see what the store holds by size, kubectl -n scrap exec deploy/scrap -c jobs -- scrap gc --report (it reads only).

After upgrading to a scrap with #572. The JPEG a photo’s reading sends to Claude is no longer kept (it is made from the photo, which is), and gc now deletes the ones older runs stored (sent_sha256) as unused. On a store with many, that is over gc’s safety limit (more than 10 % of the files, see The database on an emptyDir, with Litestream), so on a Litestream install the nightly gc only counts and exits 1, pushing scrap: scheduled job gc failed to SCRAP_NOTIFY_URL every night; while it is held, the trash purge, the pruning of runs and jobs and the gathering of orphaned files wait too. After a backup and a look at scrap gc (a dry run), run kubectl -n scrap exec deploy/scrap -c jobs -- scrap gc --delete --allow-large once; the nightly gc then deletes as before, with its limit.

  • Turn one off with gc.enabled: false, enrichRelated.enabled: false or enrichTopics.enabled: false (or ingest.enabled: false for both Claude jobs).

  • Change when with its .schedule and .timeZone (an empty timeZone is UTC).

  • Check them with kubectl -n scrap exec deploy/scrap -c jobs -- scrap schedule status (Are the nightly jobs healthy?) and kubectl -n scrap logs deploy/scrap -c jobs.

  • Run one now:

kubectl -n scrap exec deploy/scrap -c jobs -- scrap schedule --run gc

(or enrich-related, enrich-topics).

The database on an emptyDir, with Litestream#

The chart runs the database with Litestream (litestream.enabled: true, the default from chart 1.9.0): the database lives on an emptyDir on the node’s disk, and Litestream copies it to the data volume, so the data volume may be NFS or another network filesystem, where SQLite’s write-ahead log is not safe. Why, and the choices behind it: ADR 46. It needs Kubernetes 1.29 and pulls litestream/litestream from Docker Hub (pinned by digest in litestream.image).

  • Where things are. The database is at /db/scrap.db on an emptyDir on the node’s disk, limited by litestream.sizeLimit (2 Gi), which the WAL and Litestream’s own files share: a database over half of it is refused at start and warned of in the jobs log. A Litestream sidecar copies each change to /data/litestream on the data volume. Files and the preview cache stay on the data volume.

  • What can be lost. While Litestream is healthy, a copy follows each write by about a second: if the node dies, those last moments are lost. A clean stop or upgrade loses nothing: Litestream stops after scrap, with its last sync (terminationGracePeriodSeconds grows by 30 s; the jobs container stops its jobs within 15 s, so they never eat into it). Backups remain the protection against everything else, including a mistake that replicates faithfully.

  • If replication stalls (Litestream stays up, logging monitor error, if it cannot write), “about a second” no longer holds. The jobs container stamps the database every 15 minutes and looks each minute for a new file in the replica. With none for 20 minutes it logs REPLICATION STALLED, pushes to SCRAP_NOTIFY_URL if set, and fails its readiness probe, so the pod leaves its Service and scrap takes no more writes from outside. It comes back by itself. Writes made in those 20 minutes are not in the replica until it recovers, and are lost if the pod goes first: the next start then compares the replica with the last stamp noted on the volume, warns if it is behind, and refuses if over 30 minutes behind. This cannot see a whole volume failing, where the note cannot be written either: that shows as the same stall, and in scrap’s file errors.

  • Each start. The db-init init container keeps a database already on the emptyDir, or restores the replica. An install in the old mode (the database at /data/scrap.db) moves across on its first start, and the old file is left in place (a file with no pages does not count): see Upgrading from the old mode. A new database is made only if nothing says there should be one. A bad schedule or time zone also stops it here.

  • When a pod stays in Init. kubectl -n scrap logs deploy/scrap -c db-init says why. It fails on purpose rather than start empty: a restore failed (a damaged replica, a database from a newer scrap), or the replica is missing though the state file /data/.scrap-db-state.json says there was one, or there are files or backup runs but no database or replica, or /data/scrap.db changed, or the replica is far behind. Usually the answer is to restore a backup. If you are sure, litestream.init.override: true goes on from what is there. Set it back at once: while it is on a later loss of the replica would also start. Each use is recorded, and gc then only counts, and its run fails, until you run kubectl -n scrap exec deploy/scrap -c jobs -- scrap db-hold --clear, since what came back may be older than the files.

  • gc’s safety limit. gc deletes files nothing refers to, so a database older than the files makes the newest look unused: the one loss a restore cannot undo. So on these installs gc --delete only counts, and fails, when the database has no captures but files/ has content, or when the files to go are over 10 % of them and at least 5. After a look, kubectl -n scrap exec deploy/scrap -c jobs -- scrap gc --delete --allow-large goes ahead once.

  • Backups are CronJobs: they restore the replica to a temporary file and back that up with files/, with the same integrity check and COMPLETE marker. They never touch the live database, but they still run beside the scrap pod, for the ReadWriteOnce data volume, so they wait while scrap is scaled to zero. A replica whose heartbeat is over 3 hours old is refused, and the job fails: look at kubectl -n scrap logs deploy/scrap -c litestream.

  • gc and the Claude passes need the live database, so they run in a jobs container in the scrap pod, with their values’ schedules, read as a CronJob reads them but for @every, which is refused. An empty timeZone is UTC here, not the controller’s zone. All of them share litestream.jobs.resources: gc.resources and enrich*.resources are not used. Run one now with kubectl -n scrap exec deploy/scrap -c jobs -- scrap schedule --run gc (or enrich-related, enrich-topics). A failure is in kubectl -n scrap logs deploy/scrap -c jobs, in scrap schedule status and its metrics (Are the nightly jobs healthy?) and, if set, SCRAP_NOTIFY_URL, not a failed Job; a Claude pass stopping at a queue pause or a spent budget is logged, and is not a failure. gc still deletes only with a recent COMPLETE backup, otherwise only counts. A time missed while the pod is restarting is not made up, and a rollout stops a running pass: the next run carries on, so a rollout around 04:30 skips that night’s gc, and one on a Sunday around 04:11 that week’s topics.

  • A jobs container that keeps crashing takes scrap out of its Service, as Litestream’s does: nothing would then be watching replication.

  • Do not set litestream.enabled: false, or helm rollback to a chart before 1.7.0. /data/scrap.db is then an old copy: scrap refuses to start on it while the state file is there, and a chart from before 1.7.0 cannot check, so it serves the old file and its gc deletes files only the newer database uses.

Are the nightly jobs healthy?#

With no Job objects for gc and the Claude passes, scrap schedule records each run in the database (so the record survives the pod), and reports it:

kubectl -n scrap exec deploy/scrap -c jobs -- scrap schedule status

JOB             SCHEDULE              LAST RESULT  LAST START        LAST END          LAST OK           NEXT RUN          NOTE
gc              30 4 * * * UTC        ok           2026-11-07 04:30  2026-11-07 04:31  2026-11-07 04:31  2026-11-08 04:30
enrich-related  41 3 * * * UTC        paused (1)   2026-11-07 03:41  2026-11-07 03:52  2026-11-06 03:58  2026-11-08 03:41
enrich-topics   11 4 * * 0 UTC        ok           2026-11-01 04:11  2026-11-01 04:13  2026-11-01 04:13  2026-11-08 04:11
Backups: newest COMPLETE run 20261107T033000Z, marked 2026-11-07 03:34 (9.1 h ago)
Times are UTC; now 2026-11-07 12:40.
All healthy.

A result is ok, failed (a non-zero exit), deadline (stopped at its deadline), not-started, paused (a Claude pass stopped at a queue pause or a spent budget: not a failure) or stopped (with the pod: the next run carries on). NOTE says running while a run holds the job’s lock, never run, and INTERRUPTED when the last run started but recorded no end and is not running (the pod was killed mid-run, as at a node’s death: a clean stop records stopped). --json gives the same as JSON. It exits 1 and lists the problems when a job’s last run failed, was stopped at its deadline, could not start or was interrupted; when a job is stale, with no success in either of its last two runs that should have ended by now (each scheduled time plus its deadline: a paused run is not a success, so a pause that lasts two runs counts; a new job counts from when the scheduler first saw it); when the newest COMPLETE backup run is over 26 hours old, or there is none (past 26 hours gc only counts); or when the records cannot be read. So it serves as a probe or a check from any monitor that can run kubectl exec. The backups are visible only with backup.enabled (SCRAP_BACKUPS); otherwise it says not visible here.

Metrics. litestream.jobs.metrics.enabled: true has the jobs container serve Prometheus metrics on GET /metrics at litestream.jobs.metrics.port (9464), at the pod’s IP: not in the Service, not through the ingress. The pod gets the prometheus.io/scrape, /port and /path annotations unless .podAnnotations: false (or use a PodMonitor on the metrics port). With networkPolicy.enabled, list your Prometheus in .from (NetworkPolicy peers), or the port stays shut. Without a NetworkPolicy, any pod in the cluster can read /metrics: it holds only job names, results and times, but turn networkPolicy.enabled on if that matters. It listens on IPv6 and IPv4 where the pod has both. Each scrape reads the records afresh; per job (label job):

Import a large export#

The app imports a zip of up to the upload limit (maxUploadMB, 50 MB): Import your pages. For a bigger one, such as a full export of another store, run scrap import in the scrap pod. It is safe while scrap runs: the import adds each page in its own transaction to the same database the server uses, a page added meanwhile is skipped, and Litestream copies the writes as it copies the server’s.

With the script#

deploy/scrap-import.sh needs only kubectl:

curl -fsSLO https://raw.githubusercontent.com/gilesknap/scrap/main/deploy/scrap-import.sh
sh scrap-import.sh notes.zip            # a dry run: writes nothing
sh scrap-import.sh --apply notes.zip    # the import

It finds the one Ready scrap pod (SCRAP_NAMESPACE and SCRAP_RELEASE, both scrap by default), checks that its database is there, streams the zip into the jobs container’s /tmp and checks its size, then runs scrap import --dry-run, or the import with --apply. It always removes the zip. --enrich and --photos are passed on: they have Claude tag and summarise the new pages, and read their photos, which costs money and counts against ingest.budgetDayUSD. Without them Claude is not called. Ctrl-C stops the script and removes the zip, but an import already running in the pod may finish: that is safe, as it only adds, and a re-run skips the pages it did. If the script is killed outright, remove what it left with kubectl -n scrap exec deploy/scrap -c jobs -- sh -c 'rm -f /tmp/scrap-import-*.zip'.

By hand#

  1. Find the pod, and check that exactly one is Ready: kubectl -n scrap get pods -l app.kubernetes.io/instance=scrap,app.kubernetes.io/name=scrap.

  2. Copy the zip into the jobs container’s /tmp. The root filesystem is read-only, and /tmp is an emptyDir limited to 1 Gi, so keep the zip under about 900 MiB, or split the export:

    kubectl -n scrap exec -i <pod> -c jobs -- sh -c 'cat > /tmp/notes.zip' < notes.zip

  3. Run a dry run, read its list of pages and problems, then run it again without --dry-run:

    kubectl -n scrap exec <pod> -c jobs -- scrap import --dry-run /tmp/notes.zip
kubectl -n scrap exec <pod> -c jobs -- scrap import /tmp/notes.zip

  4. Remove the zip: kubectl -n scrap exec <pod> -c jobs -- rm /tmp/notes.zip.

The jobs container has the same SCRAP_DATA_DIR and SCRAP_DB_PATH as the server, so pass neither. Do not pass --data-dir on its own: it means the database in that folder, /data/scrap.db, not the live /db/scrap.db. The new pages’ files go on the data volume and the pages into the database on /db, within litestream.sizeLimit: kubectl -n scrap exec deploy/scrap -c jobs -- scrap gc --report shows the sizes. In the old mode (litestream.enabled: false) there is no jobs container: use -c scrap, as the script does. The zip then shares the server’s /tmp with large uploads, so keep it well under the limit, or import when nobody is uploading.

k3s and storage notes#

  • k3s’s default local-path provisioner keeps the volume in a directory on one node and pins the pod to that node: if the node is down, scrap is down. That is fine for a home cluster; move the data with a backup and restore.

  • local-path does not apply fsGroup; its directories are world-writable, so uid 10001 can still write. On other storage the chart’s fsGroup: 10001 makes the volume writable.

  • The database is on the node’s disk (an emptyDir), never on the data volume, so the data volume can be any ReadWriteOnce storage, NFS included (The database on an emptyDir, with Litestream). The node needs room for it (litestream.sizeLimit). ReadWriteOncePod volumes would keep the backup jobs out; use ReadWriteOnce.

  • Mixed arm64 and amd64 nodes (e.g. ARM boards and an x86 mini PC) need no settings: the image is multi-arch. Use nodeSelector only to choose where the data lives.

Argo CD#

A generic Application that installs the released chart from ghcr.io (replace the placeholders, and pin targetRevision to a release version; a pre-release 0.4.0rc1 is chart version 0.4.0-rc.1). The chart version and appVersion come from the git tag, so the image tag follows with no image.tag set. A Git source (repoURL: https://github.com/gilesknap/scrap.git, path: charts/scrap) also works, but the checked-in chart has appVersion 0.0.0, so set image.tag too:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: scrap
  namespace: argocd
spec:
  project: default
  source:
    repoURL: ghcr.io/gilesknap/charts
    chart: scrap
    targetRevision: <release-version>
    helm:
      valuesObject:
        ingress:
          enabled: true
          className: tailscale
          tls:
            - hosts: [scrap]
        ingest:
          enabled: true
          existingSecret: scrap-secrets
        litestream:
          enabled: true
  destination:
    server: https://kubernetes.default.svc
    namespace: scrap
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Both claims carry two annotations by default, and keep them if you set your own persistence.annotations or backup.persistence.annotations:

  • helm.sh/resource-policy: keep: helm uninstall leaves the claim, and Argo CD treats it as Delete=false, so deleting the Application leaves it too (Argo CD and Helm).

  • argocd.argoproj.io/sync-options: Prune=false: with prune: true, Argo CD deletes any object that drops out of the rendered chart, which is what a claim does when you switch to persistence.existingClaim or set backup.enabled: false. This annotation stops that (sync options); Helm ignores it. Delete a claim you no longer need by hand.

Also use a StorageClass (or set the PV) with the Retain reclaim policy: k3s’s local-path defaults to Delete, so a deleted claim takes the data with it.

Uninstall#

helm uninstall scrap -n scrap

removes the Deployment, CronJobs, Service, ServiceAccount, Ingress and NetworkPolicy, but keeps both claims (data and backups), because they are annotated helm.sh/resource-policy: keep. The namespace and the Secret you created stay too. Installing again with the same release name reuses the surviving claims.

To delete the data for good, first copy a final backup off the cluster, then delete the claims:

kubectl -n scrap get pvc
kubectl -n scrap delete pvc scrap-data scrap-backups

Use the names get pvc shows (<fullname>-data and <fullname>-backups). A claim you supplied with persistence.existingClaim or backup.persistence.existingClaim is not the chart’s to delete. What happens to the underlying volume depends on the StorageClass reclaim policy: with Delete (k3s’s local-path) it goes with the claim, with Retain it stays, and you remove the PersistentVolume by hand.

What the chart does not do#

  • Run more than one replica, or any high availability: SQLite has a single writer.

  • Create Secrets, take the API key as a value, or log in users.

  • Expose scrap to the internet, or add authentication. Public pages (Public pages) put only the static site of the pages you mark Public on the internet, never scrap.

  • Copy backups off the cluster.

  • Restrict egress (ingest needs api.anthropic.com, and any public site a saved link points to while SCRAP_ENRICH is on; notifications need your notify URL).

  • Run gc, the related pass or the topics pass without the scrap pod running: they run in its jobs container (see Scheduled gc, related pages and topics).

  • Publish a Helm repository: releases publish the chart as an OCI artifact only (oci://ghcr.io/gilesknap/charts/scrap); a checkout or a Git source also works, with image.tag set.
