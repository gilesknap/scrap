Scheduled jobs#

What runs on a schedule, on both deployments: a Kubernetes CronJob from the Helm chart (Deploy on Kubernetes), or a systemd user timer on a single server (Deploy on a single server). <fullname> is the release’s full name (scrap for a release named scrap), shortened with a hash when it is long.

The default night, in order (times are the chart’s; each single-server timer adds up to 15 minutes of random delay). Gc looks for the backup before it deletes:

No

gc

<fullname>-gc

scrap-gc.timer, scrap-gc.service

04:30 daily, 30 4 * * *

scrap gc: deletes stored files nothing uses and old run records, purges pages in the trash past trashDays (topic pages aside) and finished job records past jobDays, gathers files no page shows onto the month’s Orphaned assets page; deletes only after a completed backup less than 26 hours old, else only counts and fails (Deleting unused files (scrap gc))

No

Kubernetes: starts within 1 h, runs at most 1 h; single server: 1 h

Related pages

<fullname>-enrich-related

scrap-enrich-related.timer, scrap-enrich-related.service

03:41 daily, 41 3 * * *

scrap enrich --related: picks related pages for every page changed, or with a photo read, since its last picks (Related pages). It does not write board write-ups again: an outdated one is the owner’s to regenerate

Yes

Kubernetes: starts within 1 h, runs at most 4 h; single server: none

Topics

<fullname>-enrich-topics

scrap-enrich-topics.timer, scrap-enrich-topics.service

04:11 on Sundays, 11 4 * * 0

scrap enrich --topics: one discovery call (new topic pages and sources), then a synthesis queued for each topic due, which the scrap service’s worker makes (Topic pages)

Yes (the call, and the syntheses)

Kubernetes: starts within 1 h, runs at most 1 h; single server: none

Settings#

Each chart value, its default, and what does the same on a single server. A timer drop-in is systemctl --user edit <timer> with [Timer], an empty OnCalendar=, then the new one; a service drop-in is systemctl --user edit <service> with [Service], an empty ExecStart=, then the new command (both in Backup and restore, Changing the schedule and Changing what a job does). Re-running install.sh enables again every timer whose command the image has, so a timer turned off only with systemctl --user disable must be disabled again after it; SCRAP_BACKUP_MONTHLY_KEEP=0 is an opt-out that install.sh keeps.

Notes#

  • One budget. The Claude jobs spend from the same daily budget as photo ingest and text enrichment, SCRAP_BUDGET_DAY_USD (ingest.budgetDayUSD in the chart, default $3 a UTC day). Each stops at a queue pause or when the day’s budget is spent, and exits non-zero then; the next run carries on.

  • Claude jobs need ingest. The chart creates the related-pages and topics CronJobs only while ingest.enabled is true. A single server’s timers run regardless; while ingest or enrichment is off, or no key (or seat token) is set, the command says so and succeeds.

  • Spacing. Backup 03:30, related pages 03:41, monthly backup 03:50 on the 1st, topics Sundays 04:11, gc 04:30 (each timer with up to 15 minutes of random delay): gc comes after the backup it checks for, the two backups and gc share a lock so never overlap, and the Claude jobs usually start after the backup has its copy (nothing orders them: a slow backup may overlap).

  • Deadline. In the chart, a CronJob that cannot start within an hour of its time (startingDeadlineSeconds) is skipped, and a Job is stopped after its run time (activeDeadlineSeconds). On a single server, the backup, monthly backup and gc services stop after an hour (TimeoutStartSec); the Claude ones have no limit.

  • Time zone. In the chart, an empty timeZone uses the cluster’s clock (the controller’s, usually UTC); set an IANA name such as Europe/London to change it. A single server’s timers use the machine’s local time.

  • Single-server schedules. Change one with a timer drop-in, which install.sh keeps: systemctl --user edit scrap-backup.timer, then clear OnCalendar before the new one (Backup and restore, Changing the schedule). The same works for every timer.
