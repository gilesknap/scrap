# HTTP API and CLI

Reference for scrap's HTTP API, command line and settings. Requests and responses are JSON unless noted.
Responses of text (JSON, the PWA's scripts, styles and pages) over 1 kB are gzipped for a client
that sends `Accept-Encoding: gzip`; stored files, previews, downloads, fonts and range requests
never are.
The service listens on `127.0.0.1`, or with `scrap serve --uds` only on a Unix socket (the
single-server install's default), and has no login; put Tailscale Serve (or an authenticating
proxy) in front. The author of a capture or edit is the `Tailscale-User-Login` header (or the header named by
`SCRAP_IDENTITY_HEADER`), else `tagged`.

## HTTP

### Errors

An error is a JSON body `{"detail": ...}` with the status that says what went wrong:

- `400`: a multipart text field (`text`, `url`, `title`...) over 1 MiB, refused by the form
  parser before scrap sees it; the body is `{"detail": "Part exceeded maximum size of 1024KB."}`.
  A JSON body of that size is `422` instead (see `POST /api/captures`).
- `404`: no such page, capture, photo, drawing version or stored file. A page in the trash is not
  found either, except by the undelete route. So is a path that is neither under `/api` nor one of
  the PWA's routes below, and a PWA route with a trailing slash (`/todos/`): `{"detail": "Not
  Found"}`, with no fallback to the PWA.
- `409`: a conflict. A stale page edit (`rev` in the body is the current revision) or a stale
  drawing edit (`version` is the current version); also *Ask Claude* while enrichment is off.
- `413`: over the upload limit (`SCRAP_MAX_UPLOAD_MB`) or, for a drawing, 8 MB.
- `422`: invalid. `detail` is a string for a rule scrap checks, but a list of validation errors
  for a malformed query parameter or body (for example `limit=501` on `GET /api/pages`).
- `503`: as listed for the route (the worker has stopped, the PWA is not built, the preview decoder
  is busy). The one error that is not JSON is the PWA-not-built `503`, which is plain text: the
  build command, `npm --prefix web ci && npm --prefix web run build`, and a note that the API
  works without it. The service logs the first line of it as a warning at start. Without the PWA,
  `/api`, `/healthz` and `/mcp` work as usual.

Stored files and previews are content-addressed, so they are served with `Cache-Control: private,
max-age=31536000, immutable`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy:
sandbox` (an uploaded HTML file cannot run scripts). A SHA-256 is 64 lower-case hex digits (the
`uses` and drawing routes also take upper case); any other value, or a file not stored, is `404`. A page download is `Cache-Control: no-store`. The
PWA's hashed files under `/assets/` are `immutable`; its other files are `no-cache`, so a new
build is noticed.

### The page object

`GET /api/pages/{id or slug}` (and every route that returns "the page") gives `id`, `slug`,
`title`, `body`, `kind`, `kind_fixed`, `fields`, `created_at`, `updated_at`, `rev`, `tags`,
`removed`, `tasks` (`{done, total}`), `due`, `priority` and `snoozed_until` (`null` unless a
todo), and:

- `captures`: each with `id`, `kind` (`note`, `url`, `photo` or `file`), `text`, `url`, `source`,
  `author`, `created_at`, `received_at` and `blobs`: one `{sha256, mime, size, filename, ingest}`
  per file, where `ingest` is as described for the route below.
- `model_tags`: the tags Claude added that are still on the page.
- `related`: pages Claude picked, pages that link here, pages a board's write-up links to or
  whose write-up links here, and pages a topic's synthesis cites or topics whose synthesis cites
  this page, each `{id, slug, title, kind, via}` (`via`: `claude`, `link`, `both`, `writeup` or
  `topic`).
- `enrich`: `{on, state, error, reason, summary, producer, source, at}`, or `null` if the page was
  never asked about and enrichment is off. `state` is `queued`, `processing`, `done`, `failed` or
  `paused` (queued while the shared queue is paused: `reason` says why, as in `GET /api/ingest`).
- `writeup`: Claude's write-up of a board page (a whiteboard or diagram image, not a list of
  actions): `{board, on, guidance, state, error, versions, outdated, current}`, or `null` for a page with
  none and no board. `board`: whether one can be written; `on`: enrichment is on; `guidance`: the
  owner's for the next one; `state`: its latest write-up or Ask job's, as `enrich.state`;
  `versions`: how many; `outdated`: the current write-up is outdated, as `is:outdated` has it (a
  board image read, or the page's text, title, kind or tags changed, since it was made, or an
  older prompt; never one the owner restored; always `false` for a topic's synthesis, which the
  weekly pass remakes); `current`: `null` or `{version, producer, created_at, prompt_version,
  summary, text, guidance, restored_from, links}` (`text` is Markdown, its links `[[slug]]`;
  `links`: the slugs of the pages, not in the trash, it links to: the PWA links no others).
  A topic page's synthesis is its write-up: the same object, with `topic` true (`board` false).
- `topics`: the topics (not in the trash) the page is a source of, each `{id, slug, title}`.
- `topic`: `null`, or for a topic page (one Claude made for a recurring thing, its `body` the
  owner's notes: see {ref}`ingest-topics`) `{key, sources}`, `sources` each `{id, slug, title,
  kind, added_by, added_at, excluded}` (not in the trash; `excluded` 1: the owner took it out).

The rows of `GET /api/pages` and of a search are the page without `body`, `captures`, `tags`,
`removed`, `rev`, `model_tags`, `related`, `enrich`, `writeup`, `topics` and `topic`, plus `thumb`; search rows also have no
`kind_fixed` or `created_at`, and have a `snippet`, and `topic` as a boolean: whether it is a topic page.

| `POST /api/captures` | Save a capture as a new page. JSON `{id, text?, url?, kind?, source?, created_at?, due?, priority?, snoozed_until?, tags?}`, or `multipart/form-data` with the same fields (a `tags` field per tag) plus one or more `file` parts (`file`, singular; `POST /share` takes `files`). `id` is a ULID minted by the client (any case; stored upper case): `201` the first time, `200` with the same reply on a retry. The `id` is all a retry is matched on: the repeat is checked like any request (`422` if it is invalid), then answered with the first save's reply and its text, files and tags thrown away, so changed content needs a new `id` (files sent with a retry are stored, but no page uses them; `scrap gc` clears them). `kind` (`note`, `todo`, `consume`, `whiteboard` or `document`) is the user's choice: it fixes the page kind (`kind_fixed`, so ingest keeps it) and fills its default `fields`; without it the page is an unfixed `note`. `hint` (`todo` or `consume`) is the older name for `kind`, still accepted. `source` is `pwa` (the default) or `share`; `mcp` is refused here: only the MCP server writes it, so it marks a page Claude wrote. `due`, `priority` and `snoozed_until` are a todo's only (as for `PATCH`; `422` with another kind). `tags` (a list of strings) are the new page's tags, cleaned as `PATCH` cleans them (`422` for a bad one, and nothing is saved), indexed at once; Claude's tags for a photo join these on its first reading of it (a later Reprocess adds them only to a page with none, so a tag the user took off stays off). A bare URL sent as `text` is treated as `url`. The capture's own kind is derived: `photo` if all its files are images, `file` for any other files, else `url` if it has a `url`, else `note`. A file part sent with no content type, an empty one or `application/octet-stream` is typed from its filename's extension, else kept as `application/octet-stream` (so it is a `file`); and a file's stored type is the one it was first saved with, whatever a later upload of the same bytes says. For each image file, `![](/api/blobs/<sha256>/preview?size=2048)` is added to the end of the page's `body`, after the `url` and `text` (once per distinct image, and not for one the text already links by its address), so the `body` of the page is longer than what was sent (see {ref}`images-in-the-text`). The page's `title` is the first line of `text` without a leading Markdown heading marker (`#` to `######` and a space), at most 200 characters; else the `url`; else `created_at` as `YYYY-MM-DD HH:MM`, in the offset it was sent with (UTC if it was not sent). The slug is made from that title once and stays when the title is edited (see [](../explanations/design.md)); Claude may replace the title of a photo with no text, or of a saved link, with its own. `422` also for an `id` that is not a ULID, a `created_at` that is not ISO 8601, a capture with no text, url or file, a request that is neither JSON nor `multipart/form-data`, and a JSON body that is not an object. Returns `{capture_id, page_id, slug}`. `413` over the upload limit; `422` if the page's text (the `url` and `text`) is over 1 MB of UTF-8, before any file is kept. Files are stored as sent (HEIC too) |

| `GET /api/pages/{id or slug}` | A page with `rev` (its current revision), `tags` (most used first), `removed` (the SHA-256s of files an earlier revision's text referred to and the current text does not: the PWA no longer lists them), and its captures, each with its files as `blobs` (see {ref}`the page object <api-page-object>`, which also lists `model_tags`, `related` and `enrich`). | `POST /api/pages/{id or slug}/captures` | Add photos to a page that exists: the page editor's **Add photo**. `multipart/form-data` with `id` (a ULID minted by the client: the retry key, as for `POST /api/captures`), one or more `file` parts, all images (typed as for a capture), and `source?` and `created_at?` as for a capture; `415` for any other file, and nothing is saved. The images become a `photo` capture of the page, received now, so they come after the page's own (captures are in the order the server received them). For each image the text does not show already, `![](/api/blobs/<sha256>/preview?size=2048)` is added to the end of `body` as it is now, all in one new revision by the caller (none if there is nothing to add). No revision is checked (a `base_rev` sent is ignored): appending loses nothing. The photos are queued for Claude as a capture's are, and are read and searched, but never change the page's kind, title or tags, nor whether enrich or ingest maintains it: a page's first capture decides that (see [](../explanations/ingest.md)). `404` for an unknown page or one in the trash; `422` for a topic page (its synthesis is its write-up, which a board photo would replace), an `id` that is not a ULID or is another page's capture, no file, a bad `source` or `created_at`, a request that is not `multipart/form-data`, or a `body` that would be over 1 MB; `413` over the upload limit. Returns the page (as `GET` does) with `appended_on`, the revision the embeds went onto (the page's revision before, so a client holding it can take them into its own text): `201`, or `200` with the page as it is now and `appended_on` `null` on a retry with the same `id` |
| `PATCH /api/pages/{id or slug}` | `{base_rev?, title?, body?, kind?, fields?, tags?, tags_shown?, due?, priority?, snoozed_until?}`. A `title` or `body` writes a new revision and needs `base_rev`: `409` with the current `rev` if it is stale (and nothing in the request is saved). A `title` has runs of whitespace collapsed to single spaces; one that is empty or only whitespace is `422` (`title must not be empty`) and nothing in the request is saved. A `title` equal to the title at `base_rev` counts as unchanged, so it never undoes a title Claude set meanwhile. The slug does not change with the title. `kind` (as for a capture) sets `kind_fixed` (ingest then never changes it); a different kind keeps every field the page has and adds that kind's defaults for keys it lacks: `todo` `{"status": "open"}`, `consume` `{"subtype": "read", "status": "open", "source"}` (`source`: the capture's URL, if any). A default is added only if the page has room (at most 32 fields): a page with 31 fields gets one of them, a full one none, and a field the page has is never dropped for it (so the change is not a `422`). So nothing is lost by changing a kind and back; a `status` already there keeps its value. `fields` changes them, e.g. `{"status": "done"}` ticks a todo; a `null` value removes one; names are 1 to 40 characters, values flat (a string of at most 200 characters, a number or a boolean; a whole number is within ±2^53 and any other finite, so `NaN`, `Infinity` and `1e400` are `422`), and a page has at most 32 fields (`422` otherwise). `tags` replaces all the page's tags (`[]` removes them), each cleaned as an import's are (one space between words, no leading `#`, lower case, 1 to 64 characters, each once; at most 64 tags, `422` otherwise). A tag Claude added that is not in `tags` is taken off for good (Claude never adds it back); with `tags_shown`, the tags the editor started from (the PWA sends them), one Claude added that is in neither list is kept instead, since the user never saw it. `due` (a date, `YYYY-MM-DD`: no time, no time zone) and `priority` (`high`, `medium` or `low`) and `snoozed_until` (a date: out of the Todos screen's Now and the Todos tab's count until that day; it is kept, and harmless, after it) are a todo's own columns, not fields: sent, they set it, `null` clears it, not sent keeps it; a value is `422` on a page of another kind (after any `kind` in the same request: `{"kind": "todo", "due": ...}` works), as is a malformed one. A page that stops being a todo keeps them (a stray tap loses nothing), but they are ignored, and returned as `null`, until it is one again. Neither `kind`, `fields`, `tags`, `due`, `priority` nor `snoozed_until` is a text revision, nor changes `updated_at`; a change of `kind` or `tags` is a metadata revision (`page_meta_rev`: who, kind and tags before and after; see [](mcp.md)), as Claude's are, so it can be seen and reverted over MCP. A `body` (here, in a capture or over MCP) is counted for its task boxes, `tasks: {done, total}` on the page and its rows (exactly as the PWA draws them: a list item whose first line starts `[ ]` or `[x]` as typed; none in code, escaped `\[ ]`, or a link named `[x]`): a `note` whose kind nobody chose (`kind_fixed` 0: no `kind` was ever sent for it; the PWA sends one only when the user picks a kind, never for boxes) that has boxes becomes a `todo`, filed as a new capture of that text would be (all ticked: `done`); a todo's `status` becomes `done` when the last box is ticked, and, on a done one whose boxes were all ticked, `open` again when one is unticked or a new unticked one is added (a todo marked done by hand with some boxes unticked stays done); never on a `cancelled` one; a status set by hand ticks no box, and a `fields.status` in the same request as the `body` is kept, whatever its boxes. A `body` over 1 MB (1,000,000 bytes) of UTF-8 is `422` (a page's text is at most that, however it is written; nothing in the request is saved), unless it is exactly the page's current body, so a page imported over the limit can still be retitled, retagged or given another kind. Returns the page |

| `GET /api/search?q=...&limit=20&offset=0` | `limit` at most 100; `offset` (at most 10 000) skips that many hits, for the next page. Full-text search of titles, tags, the `summary` field, bodies and what Claude read from photos (their text and descriptions): every word must match somewhere in the page, as a prefix (`vsc` finds `vscode`), wherever it stands in the query; one hit per page. this includes forms the PWA draws as plain text) and `is:outdated` (a board page's current write-up older than a reading of its board images or a change to its text, title, kind or tags, or made with another prompt version, never one the owner restored; not a topic's synthesis or related pages, which their passes refresh), `image:K` (a photo Claude took for kind `K`: `photo`, `whiteboard`, `handwriting`, `diagram`, `screenshot`, `document`, `other`), `after:D` and `before:D` (last edited on or after, on or before `D`: a date `YYYY-MM-DD`, a UTC day with both ends included, or a time ago such as `1d`, `2w`, `1m` (30 days), `1y` (365 days): the number is 1 to 100 (so `100y` works but `101y` and `1000d` match nothing), at most three digits, and may be left out for 1; a value that is neither matches nothing, and after `-` everything) or `date:created` (`after:` and `before:` use the creation date instead), `due:D` (a todo due on `D` (also written `=D`), or with `<`, `<=`, `>`, `>=` before or after it: `D` is a date `YYYY-MM-DD` or `today`, `tomorrow`, `yesterday` on the server's own calendar, its local time zone (`TZ`); `due:<today` is overdue; `due:none` a todo with no due date; another value matches nothing), `priority:P` (a todo's: `high`, `medium`, `low`, or `none`; two mean either; Thoth's `urgent` means `high`); a filter after `-` excludes. `sort:updated` (last edited first), `sort:created` (newest first), `sort:title` (A to Z, ignoring the case of ASCII letters only: `é` and `É` sort apart), `sort:due` (soonest first) or `sort:priority` (high first; for both, pages without one, and pages that are not todos, come last either way) orders the results instead of best match (or newest first), with `-sort:` the other way (`-sort:created`: oldest first); the last one counts, and another value is ignored. `sort:` alone lists every page in that order. Filters alone list their pages, newest first, with the summary or the start of the text as the snippet. Words without a letter or digit (`&`, `?`) are ignored. At most 64 distinct words and 64 filters are allowed: a query with more is refused with a 422 (nothing is searched), so a NOT word or `-tag:` is never silently left out. A filter with no value (`tag:`) is ignored. Tags have no empty path segments: `/lead`, `trail/` and `a//b` are stored as `lead`, `trail` and `a/b`, and `tag:/` matches nothing. Each hit has `id`, `slug`, `title`, `kind`, `fields` (so a todo's row can show its status), `due`, `priority`, `snoozed_until`, `tasks`, `updated_at`, `thumb` (as in `GET /api/pages`), `topic` (whether it is a topic page: the PWA labels it) and an HTML-escaped `snippet` with matches in `<mark>` |
| `GET /api/search/facets?q=...&top=12` | What the pages a search finds have in common: `{total, kinds: [[kind, n]], tags: [[tag, n]], personal: {work, personal}, active: [{token, key, value, neg}]}`. `tags` are the `top` most used (12 unless asked, at most 1000) (a tag counts for its parents too, `a` for `a/b`), leaving out those the query asks for (its `tag:` filters, not `-tag:`) and those on every page found (unless only one page is found, when all its tags are given); `active` are the query's filters as typed (`sort:` too) |
| `GET /api/health` | The store's health checks, each one count of the pages (not in the trash) its search finds: `{checks: [{term, count}]}` with `term` `is:orphan`, `is:untagged`, `is:stale`, `is:duplicate`, `has:dangling` and `is:outdated` (a board's outdated write-up only, not related pages or a topic's synthesis, which their passes refresh), in that order (the PWA's Store health screen). One query a check; nothing is stored and no model is called |
| `GET /api/tags` | Every tag on a page not in the trash, with the parents of `a/b` tags, how many pages have it (or one under it), and how many have that very tag (`0` for a parent no page was given): `[[tag, n, own]]`, in order |
| `GET /api/pages/{id or slug}/download` | The page to keep: `<slug>.md` (front matter, with a todo's `due`, `priority` and `snoozed_until` if it has them and its `tasks` count if it has task boxes, then the body), or if it has files `<slug>.zip` holding the `.md` and `files/` with the originals, linked relatively so it reads offline. Each file keeps the name it was uploaded under, made safe: any folder part is dropped, a run of characters other than letters, digits, `_`, `.`, space and `-` becomes one `_`, and the name is cut to 120 characters; a file with no usable name is named by the first 12 characters of its SHA-256 and an extension from its type. When two names are the same ignoring case, the later gets `-2`, `-3`... before the extension (`scrap export` names files differently: see {ref}`api-cli-folders`). Each photo is followed by Claude's description (a quote) and the text it read (a fenced block), and its drawing is beside it as `<photo name>.excalidraw` (Claude's skeleton converted approximately on the server: Excalidraw re-measures the text when it opens it) |
| `GET /api/blobs/{sha256}/uses?page={page id}` | `{pages}`: how many pages other than `page` (the trash left out) show the file, by an embed in their text or as a file of their own capture. The editor's warning when an embed is deleted. `404` if the file is not stored |
| `GET /api/blobs/{sha256}` | An original file, byte for byte, with its stored content type. `?download=1` adds a `Content-Disposition` with the name it was uploaded under, made safe as for a page download |
| `GET /api/blobs/{sha256}/preview?size=2048` | A JPEG of a photo (HEIC too), turned upright and without its EXIF, at most `size` (`480` or `2048`) pixels a side. Made on first request and kept in `cache/previews/` under the data folder, which is never backed up and can be deleted at any time. Made one at a time, shrunk as it is decoded, within a memory budget that fits a 1 GB container: `422` for another `size`, if the file is not an image Pillow can read or would need more memory than that to decode (roughly over 50 megapixels for HEIC, 80 for PNG; JPEG is decoded shrunk and fits at any size), `503` with `Retry-After` if the decoder stays busy for 20 s. The colour profile is kept |
| `GET /docs`, `/redoc`, `/openapi.json` | FastAPI's interactive documentation (Swagger UI and ReDoc) and the OpenAPI schema, generated from the routes. The PWA, `/share` and `/mcp` are not in them, nor are the request bodies of `POST /api/captures` and the drawing `PUT`, and most responses are only `object`: this page is the fuller description. Open to anyone who can reach the service, like the rest |
| `POST /mcp` | The MCP server (Streamable HTTP, stateless, JSON replies) for Claude Code sessions: see [](mcp.md). `401` if `SCRAP_MCP_TOKEN` is set and no matching bearer token is sent, `421` if the `Host` header is not loopback or a `SCRAP_PUBLIC_URL` host, `403` for another `Origin`, `413` over 2 MB |
| `POST /share` | The PWA's share target, for when its service worker did not take the share (which it normally queues itself): saves the multipart `title`, `text`, `url` and `files` as a capture with a server-minted id (source `share`), then `303` to `/`; other fields are ignored. The fields are trimmed. With no `url`, a link that ends `text` after whitespace (where Android puts it) moves to `url`; a `title` that is not already in `text` goes first, with a blank line after it; a file part with no content is skipped. The page is then made as for `POST /api/captures` (titles, image embeds, `413` over the upload limit, `400` for an over-large text field). A share with no text, url or file saves nothing and still answers `303`, so the status cannot tell a saved share from an empty one |
| `GET /`, `/recent`, `/search`, `/tags`, `/todos`, `/topics`, `/p/{slug}` | The PWA (`index.html`; `/recent` and the retired `/tags` open Search); its other files are served from the root too. `503` with build instructions if it was not built; see [](../how-to/use-the-pwa.md) |

(api-cli-status)=
### Exit status and common errors

A command that works exits `0`. One that refuses prints a single line on stderr and exits `1`.
Arguments it cannot use (`scrap enrich` with neither or both of `--backfill` and `--related`, an
unknown option) print the usage and exit `2`. `scrap` alone prints the help and exits `0`.

`scrap serve`, `restore` and `enrich` (both modes) create the data folder and bring `scrap.db` up to
date, and so does `import` unless it is a `--dry-run`, which writes nothing. `backup`, `export` and
`gc` never create or upgrade anything: with no `scrap.db` they stop at once. That makes a wrong
`--data-dir` easy to miss. With no `--data-dir` and no `SCRAP_DATA_DIR` the data folder is `./data`
under the current directory, so run from the wrong place, `serve`, `import` and `enrich` quietly
start a new empty one, while `backup`, `export` and `gc` say `no database at data/scrap.db`.

| Message | Cause |
| --- | --- |
| `no database at <data folder>/scrap.db` (`scrap gc: no database at ...` for `gc`) | `backup`, `export` or `gc` was pointed at a folder with no database: the wrong `--data-dir`, or the working directory is not the one you expected |
| `scrap gc: no files folder at <data folder>/files` | The database is there but the data folder has no `files/` |
| `scrap gc: the grace period must not be negative` | A negative `--grace-hours` |
| `scrap gc: the run retention must be at least 1 day` | A `--run-days` below 1 |
| `scrap gc: cannot read what is in use, so nothing was deleted: ...` | The database could not be read, or it is newer than this scrap |
| `scrap gc: cannot put back a file left aside by an earlier run, so nothing was deleted: ...` | A file an earlier run set aside could not be restored (permissions or disk) |
| `scrap gc: another scrap gc is deleting (it holds <data folder>/gc.lock); ...` | Another `--delete` run is in progress, such as the nightly one; try again when it ends. Counting runs take no lock |
| `no folder <path>` | `scrap import`'s `DIR` is not a folder |
| `no backup at <DIR>` | `scrap restore`'s `DIR` has no `scrap.db` |
| `bad backup: ...` | The backup's database is not a database, fails its integrity check, or has a schema newer than this scrap. The data folder is left as it was |
| `<data folder> is not empty; stop scrap and use --force` | `scrap restore` into a data folder that has a database or any file; see `--force` above |
| `stopped: the queue is paused (<reason>)` | `scrap enrich --related` met a pause or spent the day's budget (exit `1`) |

A setting scrap cannot use stops it with its own message: see {ref}`api-settings`.

(api-cli-folders)=
### Backup and export folders

`scrap backup DIR` makes `DIR` if it is missing, then replaces `DIR/scrap.db` with a fresh snapshot
(written as `scrap.db.part` and renamed, so a run that stops half way leaves the earlier database
whole) and copies `files/` (laid out as in the data folder, `files/<first two hex digits>/<sha256>`).
Files are only ever added: one already in `DIR/files/` is neither touched nor removed, and names that
start with `.` (uploads in flight) are skipped. The preview cache (`cache/previews/` in the data
folder) is not copied. So backing up again into the same `DIR` is incremental, and `DIR` goes on
holding files no page uses any more (after a `scrap gc`, say). Use a new `DIR` for each backup if
that matters; the single-server timer does, and keeps the newest `SCRAP_BACKUP_KEEP` of them (see
{ref}`scrap-backup-restore`).

`scrap export DIR` writes one `<slug>.md` per page at the top of `DIR` and one `DIR/files/` for all
the pages, in which a file is named `<sha256><extension>`, the extension being the usual one for its
content type (none if it has none). It is not the name it was uploaded under, and a file on several
pages is stored once. A photo's drawing is `<sha256>-<capture id>.excalidraw`, since a drawing
belongs to a capture. The page download names files differently (by their uploaded names: see
`GET /api/pages/{id or slug}/download`).

Run it again into the same `DIR` and every `.md` and drawing is written afresh, while a stored file
already there is left alone. Nothing is deleted: a page put in the trash since, and its `.md`, stay in
`DIR`. Export into a new folder for a clean copy.

(api-cli-ingest-once)=
### Reading `ingest-once` output

`scrap ingest-once` prints indented JSON, and none of the text of the image except in `error`:

- `model` (`SCRAP_VISION_MODEL`, else the default), `prompt_version` and `sent`: `[width, height,
  bytes]` of the JPEG Claude received.
- `outcome`: `ok`, or the failure class of the table in {ref}`ingest-spend` (`credit`, `auth`,
  `outage`, `timeout`, `invalid`, `content`, `image` or `internal`). `error` is then its message,
  with any API key replaced by `[key]`. `seconds` is the time the call took.
- Once a reply arrived, even one that failed the checks: `served_model`, `stop_reason`, `blocks`
  (the types of its content blocks), `usage` and `cost_usd`, worked out from the price table. A
  model not in the table is priced at the dearest rate, so the cost errs high.
- With `outcome` `ok` only: `kind` (what Claude took the image for), `text_lines`, `uncertain`
  (the readings marked `(?)`), `tags` (a count), `elements_given` and `elements_kept` (drawing
  elements before and after the checks) and `warnings` (how many the checks raised: elements
  dropped, arrows left unbound).
- `save_error`, if `--save` could not write the file (a full disk); the summary is still printed.

The exit status is `0` even when the call failed, so a script must read `outcome`. With no
`ANTHROPIC_API_KEY` the call does not go out: `outcome` is `internal` and `error` is the SDK's
authentication message. An answer that fails the checks was paid for, so it is reported with its
cost, and `--save` writes it. An image that cannot be decoded (`cannot preview this file`) or a
`--save` file that exists already stops with a Python error and exit `1`, before any call.

The settings are environment variables of the service, read at start. A setting that is on or off
(`SCRAP_INGEST`, `SCRAP_ENRICH`) is on for `on`, `1`, `true` or `yes`, in any case; anything else
is off. The variables below are scrap's own; those that install scrap (the image, where it
listens, the data and backup folders) are in [](../how-to/deploy-single-server.md), and the
chart's values in [](../how-to/deploy-kubernetes.md).

| Variable | Default | Meaning |
| --- | --- | --- |
