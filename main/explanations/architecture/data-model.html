Data model and storage#

scrap keeps one SQLite database and a folder of content-addressed files. Captures, blobs and pages are the truth; derived rows cost an LLM call to remake so they are stored; chunks and the FTS index are a disposable cache.

Back to Architecture. The schema is the numbered scripts in src/scrap/migrations/: one generated baseline, baseline.sql (schema 18), plus the numbered scripts after it (none yet; the first is 0019). The code is in src/scrap/store/.

Table

Holds

page

Title, Markdown body, kind, kind_fixed, flat fields, deleted_at, plus the task counts task_done, task_total

page_todo

A todo’s typed due, priority and snoozed_until: one row per page that has at least one set, deleted when the last is cleared; removed with its page

blob

Bytes of every original and binary derived artifact at files/<sha[0:2]>/<sha>, keyed by SHA-256 so a photo shared twice is stored once

capture, capture_blob

What arrived, with a client-minted ULID as the retry key; ordered blobs per capture

derived

Versioned Claude (or human) results: ocr, description, excalidraw are written (a PDF’s or text file’s ocr is scrap’s own reading, run_id NULL: Files: read locally, for search); summary and fetched are allowed by the CHECK but reserved

page_rev, page_meta_rev

Text history and kind/tag history (see Revisions)

page_trash_rev

Each move of a page into or out of the trash (see Trash)

tag

Lower-case tags per page, 1 to 64 characters, / allowed

IDs are ULIDs, so the phone can mint them offline. Times are ISO 8601 UTC. Foreign keys are on for every connection.

Table

Holds

job, queue_state

Photo and file jobs, kind ingest or refine (queued, running, done, dead), and the single-row pause state (auth, credit, outage, budget)

model_run, enrich_run, topic_run

Every call: request, response, usage, cost_microusd, error class. topic_run covers discovery calls of no one page

enrich_job

One queued job per page; reason is capture, save, ask, backfill, related, writeup or topic (its CHECK lists them)

enrichment, model_tag, related

Summary and fetched link title; tags Claude added (on) or the user removed (off, never re-added); related pages in order

writeup, writeup_guidance

Versions of a board’s write-up (one current, never changed) and the owner’s guidance for the next

topic, topic_source

Which pages are topics (with a key never made again) and their sources, with the owner’s exclusions

Originals, derived, cache#

What can be rebuilt from what. Losing the cache costs CPU; losing derived rows costs LLM calls; losing originals is loss.

        flowchart LR
    subgraph keep["Kept forever"]
        cap["Captures"]
        blob["Blobs on disk"]
        page["Pages"]
    end
    subgraph derived["Stored, regenerable"]
        der["Derived versions"]
        enr["Summaries, write-ups"]
    end
    subgraph cache["Disposable"]
        chunk["Chunks"]
        fts["FTS index"]
    end
    cap --> blob
    blob -. "Claude call" .-> der
    page -. "Claude call" .-> enr
    page ==> chunk
    der ==> chunk
    chunk ==> fts
    classDef user fill:#e9f7ef,stroke:#2e9d5b
    classDef claude fill:#fff3e0,stroke:#e08a00
    classDef store fill:#e8f1ff,stroke:#4a7bd0
    class cap,blob,page user
    class der,enr claude
    class chunk,fts store

  • Originals (green) are never edited, and are purged only with their page, once it has been in the trash for N days (ADR 30). See ADR 4 and ADR 3.

  • Derived (orange) rows are immutable versions. A new current version supersedes the old by trigger; a restore inserts a copy. Never INSERT OR REPLACE into derived or chunk: REPLACE deletes without firing the FTS triggers.

  • The cache (blue) is rebuilt by index_all. A page has one own chunk (title, tags, summary, plain-text body), rebuilt in the same transaction as any capture, save, tag change or enrich result, so there is no index job. Each current derived text is a further chunk. Chunks are deleted and inserted, never updated.

  • What is indexed is text only. Pixels, fetched article text and raw Excalidraw JSON are not. Search itself is on Search.

Kinds and fields#

document

Doc

Search aliases doc

These five are the only kinds. A topic page is a document, identified by the topic table, not by its kind.

  • made_by is who made the page: human, claude (an MCP write), topic (Claude’s topic page) or gc (scrap gc’s review page). It is set when the page is made and a trigger refuses any change, so it is not the kind: the owner can re-kind a page Claude wrote and it stays Claude’s. is:claude and the Written by Claude badge read it (ADR 33; the page roles table in Claude calls).

  • fields is a flat JSON object: no nulls or nested values, at most 32 keys, numbers within +/-2^53. In use: status (open, in_progress, done, cancelled), subtype and source on Later, summary (an import’s or the user’s, which wins over Claude’s in the index) and origin.

  • Typed todo values due (day, YYYY-MM-DD), priority (high, medium, low) and snoozed_until (day) are typed, checked columns of the side table page_todo, so due:, priority:, is:snoozed and sort: are plain SQL (ADR 12, moved off page by ADR 36). A row has at least one value; a page with none has no row, and the SQL reads that as NULL. A snoozed todo is left out of Now and the Todos count until its day. They belong to todos (page.kind = 'todo'): another kind ignores them but keeps its row. Setting them is not a revision. Only store/todo.py names the table.

  • Task boxes (- [ ], - [x]) are counted per page into task_done and task_total. An unfixed note with boxes is filed as a todo; on a todo, ticking the last box marks it done and unticking reopens it. A cancelled todo is left alone and a status set in the same edit wins.

  • The user wins. A kind chosen at capture or in the editor sets kind_fixed, and nothing else changes it. Photo ingest, enrich (a saved link becomes Later) and task boxes only change an unfixed note; an import sets and fixes its kind.

  • Changing kind keeps every field and adds the new kind’s defaults for missing keys, so todo, note, todo round-trips. See Capture, files and import for how a kind is chosen at capture.

Identity, links and tags#

  • Slug is made from the title at creation (ASCII, lower-case, at most 60 characters, -2, -3 on collision) and never changes, so [[slug]] links survive renames. Trashed pages keep their slug. The API accepts an id or a slug.

  • Links are [[slug]] or [[slug|label]] in the body, read when needed. There is no link table: outgoing links come from scanning the body, backlinks from an instr() scan of live pages. Dangling links are allowed. Markdown is parsed by a library on both sides (ADR 14).

  • Tags are flat, lower-case, / allowed as a path; empty path segments are normalised (clean_tags). Claude’s tags are marked in model_tag and shown with a ✦; a tag the user removes is never added back and Claude never removes one.

  • Related pages come from enrich, kept apart from the text and shown both ways, merged with backlinks and a board’s write-up links.

  • Page size is capped at 1 MB of UTF-8 (MAX_PAGE in store/constants.py); the API answers 422 beyond it.

Revisions and conflicts#

Text and metadata have separate histories; neither covers Claude’s enrichment output.

        sequenceDiagram
    participant C as Client
    participant S as Store
    C->>S: PATCH title or body, base_rev N
    alt page is at rev N
        S-->>C: saved, new rev
    else page moved on
        S-->>C: 409 with current rev
    end

  • Text (page_rev): rev 1 at creation, then one per title or body change. A stale base_rev saves nothing. A title equal to the one at base_rev counts as unchanged, so a client never undoes a title Claude set meanwhile.

  • Source. Each text revision records its author and its source: mcp for Claude’s text (MCP edits and appends, and the task boxes Claude adds), else web. The source, not the author’s name, makes a revision Claude’s, and no identity header can name claude (ADR 33).

  • Window. One author’s edits from one source within SCRAP_REVISION_WINDOW seconds (default 300; 0 makes every change its own revision) fold into one. MCP edit_page takes a base_rev too (ADR 22).

  • Metadata (page_meta_rev): each kind or tag change, from the PWA or MCP, records before and after, with a batch_id shared by a bulk change. MCP revisions lists both histories and revert undoes one (ADR 19).

  • Not revisions: fields (status), due, priority, snooze, task counts, and a provisional title replaced by ingest or enrich.

Trash#

Deleting sets deleted_at. Nothing deletes a page until it has been in the trash for N days (--trash-days, 30 by default; SCRAP_TRASH_DAYS tells the server); then the nightly scrap gc --delete purges it, and the schema’s ON DELETE CASCADE takes everything on it (ADR 30).

        stateDiagram-v2
    [*] --> Live: create
    Live --> Live: edit, new revision
    Live --> Trashed: delete, MCP trash_pages
    Trashed --> Live: undelete (a page or a batch)
    Trashed --> [*]: purge, N days on (not a topic)
    note right of Trashed
        Read-only over MCP
        Keeps slug and history
        Out of search and backlinks
    end note

  • Trashed pages keep their slug (never reused), revisions and captures. MCP trash lists them, read and revisions show them read-only (trashed: true), trash_pages moves pages the user named there (up to 50 a call, as one batch) and undelete restores one, or a batch; every other tool treats them as absent (ADR 25, ADR 34). Nothing over MCP purges a page or empties the trash. Undelete also makes the page’s topics due again.

  • page_trash_rev records every move into or out of the trash (the PWA’s delete and undo, a pin that brings the Pinned page back, and MCP’s; all go through trash_in and restore_in): action (trash or restore), author, source (web or mcp), batch_id (shared by the pages one trash_pages call moved; a batch undelete’s restores carry it too) and created_at. MCP revisions lists them (trash) for a page, a batch, or in the recent-changes feed. It is not backfilled: a page already in the trash before page_trash_rev existed has no row, so it is in no batch.

  • The purge (retention.py) deletes the page row in one transaction, committed before gc reads what is in use; the cascades take its revisions, captures and file records, Claude’s results, runs and jobs, tags, search chunks, write-ups and topic memberships. Its files are then unused, and gc’s usual delete takes them in the same run (old enough, after a recent backup).

  • A topic page in the trash is never purged: its topic row (the key that stops discovery making it again) needs the page. A purged review page (Orphaned assets) lets go of the files it showed that would otherwise be orphans again: their capture_blob rows, and that photo’s derived, job and model_run rows, are deleted.

  • Finished job and enrich_job rows older than --job-days (30) go too, but each photo’s and each page’s (per reason) newest.

  • The PWA’s Trash screen (Settings), GET /api/trash and MCP trash show each page’s purge_at.

Migrations#

The schema is migrations/baseline.sql, schema 18, the 1.0 squash of the migrations 0001 to 0018 (ADR 37). It is generated from a database, never edited by hand (python -m scrap.store.baseline), and holds every table, index and trigger, the queue_state seed row and the full-text index rebuild. The migrations that built it are gone: their Python steps and store/fixes.py went with them, and the history is in the ADRs and the 0.16 tag.

Numbered scripts after the baseline are numbered by merge order with no gaps: the first is 0019_*.sql, and the number in a file’s name is BASELINE + 1 + its position (db.BASELINE, 18; tests/test_migrate.py enforces it). Script N sets PRAGMA user_version = N.

  • scrap restore runs the same check on the copy of a backup before it swaps anything in, so a backup below schema 18 is refused with that message, naming the folder given. To use one, restore it with scrap 0.16.x, which migrates it to 18, take a new backup, then use 1.0.

  • A migration after the baseline avoids rebuilding a table in Python unless a CHECK must change; plain SQL is enough and easy to fold later.

  • tests/data/schema_baseline.json is the frozen structure of the baseline, and tests/data/schema_head.json of the baseline plus the later scripts. A migration PR fails tests/test_baseline.py until it reviews the schema diff and refreezes (python -m scrap.store.baseline --snapshot).

  • Folding later scripts into a new baseline is deliberate and rare (when the live store is past them): python -m scrap.store.baseline --fold, bump BASELINE, delete the folded scripts, --snapshot.

  • The search index is a cache: a migration may drop and rebuild it rather than patch it.
