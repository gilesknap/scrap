Try scrap on a DLS workstation#

In this tutorial you run scrap on your own Diamond workstation, with no sudo, and open it from your phone. DLS workstations run RHEL 8 with SELinux enforcing and cgroups v1, are shared with other users, mount your home directory over NFS, and already have rootless podman set up with its storage on /scratch. Your phone cannot join the workstation network, so Tailscale carries scrap to it over HTTPS. Both run as you, as two containers in one rootless podman pod.

This page follows one path for a trial. The general install, with a dedicated user and a system Tailscale, is Install scrap on a server; every option, and the update, backup and troubleshooting steps, are in Deploy on a single server.

Note

What has been checked. On 22 Oct 2026 the steps up to Open it on your phone were run by hand on a DLS workstation (RHEL 8.10, cgroups v1, SELinux enforcing, podman 4.9.4, Tailscale 1.104.2): a phone on the tailnet opened the web app through Tailscale Serve and captured a photo. Since then tailscaled runs as you rather than as root in its container; that change was checked on the same pod, which kept its login and Serve setting. Ingest was not turned on. Backups (Back up) are not automated, and the systemd steps (Optional: start it at boot with systemd) have not been run end to end.

Warning

v0 of scrap has no login. Anyone who can reach it can read and change everything. Only expose it through Tailscale Serve (tailnet only, never tailscale funnel).

Check with DLS IT policy before you run Tailscale on a workstation. It connects the workstation to an outside network that IT does not manage.

How it fits together#

A podman pod is a group of containers that share one network namespace, with its own private 127.0.0.1. The pod scrap-pod holds two containers:

  • scrap-pod-app, scrap itself, listening on the pod’s 127.0.0.1:8000. Nothing is published to the workstation, so 127.0.0.1:8000 on the workstation reaches nothing.

  • scrap-pod-ts, the official Tailscale image, with --tun=userspace-networking so that it needs no network device. Tailscale Serve, in this container, publishes http://127.0.0.1:8000 on your tailnet as https://<name>.<tailnet>.ts.net.

Nothing here needs sudo. The pod maps user 10001 in its containers to you on the workstation, and both containers run as that user, so their processes and files are yours.

Why Tailscale does not run as root in its container

DLS workstations give every user the same subordinate id range in /etc/subuid. Rootless podman maps root in a container, and every id other than your own, into that range, so root in your container is the same workstation id as root in anyone else’s, and another user can become it with podman unshare. A tailscaled running as root in its container could then be signalled by other users, have its node key read, and be driven through its control socket via /proc/<pid>/root. So on these workstations, never run a long-lived container process as root, or as any id other than the one mapped to you, inside a rootless container. This page runs tailscaled as user 10001, which is you. It does not need root: Serve here only forwards to http://127.0.0.1:8000.

What runs as you#

Without sudo there is no dedicated user, so scrap, its data and Tailscale all run as you. Other users on the workstation cannot reach scrap or Tailscale: scrap listens only inside the pod, Tailscale’s control socket is inside the pod too, and their processes and files are yours, in a folder only you can open. Anything running as you can: it can podman exec into the pod, read and change all of scrap’s data, drive Tailscale, and send its own Tailscale-User-Login header to be recorded as any author. So can root and the workstation’s admins, and so can whoever owns or administers your tailnet (you, if you follow Make a tailnet). That is fine for a trial; for lasting use, follow Install scrap on a server on a machine where scrap has its own user. See Access and identity.

What you need#

  • A DLS workstation account with rootless podman working (podman info runs) and git.

  • A directory of your own on the workstation’s local disk, /scratch/<fedid>. scrap’s SQLite database (in WAL mode) needs a local disk, not NFS. Your home directory is on NFS and follows you to every machine that mounts it, so keep scrap’s data, Tailscale’s state (which identifies this machine) and any secrets on /scratch, not in your home.

  • A phone with the Tailscale app, and another device on which to run Claude Code if you want to connect it (see Check it from another device).

You do not need Python or Node: the images carry everything.

Make a tailnet#

Do not sign up with your @diamond.ac.uk address. Tailscale ties a tailnet to a custom email domain: the first person to sign up with a diamond.ac.uk address creates a tailnet that owns that domain, and everyone who signs up with one later joins it, subject to its admins’ approval (see domain ownership and user approval). It would also be treated as business use and start an Enterprise trial. Use a personal identity instead: a personal GitHub account, whose tailnet others can join only by invitation (GitHub), or a personal Google, Apple or Microsoft account.

  1. Sign up for a free Personal Tailscale account with that identity.

  2. Install the Tailscale app on your phone and log in to the same account. A phone is on one tailnet at a time.

  3. In the admin console, under DNS, turn on MagicDNS and HTTPS certificates. Note the tailnet DNS name shown there, <tailnet>.ts.net.

  4. In the admin console, under Access controls, replace the whole policy with:

    {
  "grants": [
    {"src": ["autogroup:member"], "dst": ["autogroup:self"], "ip": ["tcp:443"]}
  ]
}

Do step 4 before the pod joins the tailnet. In userspace mode, Tailscale forwards an inbound tailnet connection to any TCP port that Serve does not handle to the same port on the pod’s 127.0.0.1 (wgengine/netstack). Under the default policy, which lets every device reach every port, any device on your tailnet could reach scrap directly on port 8000, over plain HTTP and without the identity header that Serve adds. This policy lets your own devices reach each other on port 443 only, and nothing else. Replacing the policy wipes whatever was there, which is fine only because the tailnet is new; it also drops the default policy’s nodeAttrs that allow Funnel, so scrap cannot be put on the internet by mistake.

Build the image#

There is no published release image yet, so build it from a clone of the repo:

cd ~
git clone https://github.com/gilesknap/scrap.git
cd scrap
podman build -t localhost/scrap:dev .
podman run --rm localhost/scrap:dev --version

The first build downloads a large build-stage image, so it takes a while. Once releases exist you can instead podman pull ghcr.io/gilesknap/scrap:<version> and use that name in place of localhost/scrap:dev below.

Fetch Tailscale’s image too:

podman pull docker.io/tailscale/tailscale:stable

stable moves with each release. To stay on one version, use a tag such as v1.104.2 instead, here and below.

Create the pod#

Pick a name for the workstation on your tailnet, such as scrap; it becomes https://scrap.<tailnet>.ts.net. Make the folders on /scratch, open only to you, and a settings file for scrap there, readable only by you:

base=/scratch/$USER/scrap-pod
mkdir -p $base/data $base/backups $base/tailscale
chmod 700 $base
(umask 077; cat >$base/scrap.env <<'EOF'
SCRAP_PUBLIC_URL=https://scrap.<tailnet>.ts.net
TZ=Europe/London
EOF
)

Replace <tailnet> with your tailnet’s name from the admin console. The first part, scrap, must match the --hostname you give Tailscale below. SCRAP_PUBLIC_URL lets Claude Code reach /mcp through Serve; TZ makes due:today follow your day rather than UTC. See Ingest settings. The commands below use $base, so set it again in each new shell.

Create the pod, then start scrap and Tailscale in it:

podman pod create --name scrap-pod --userns=keep-id:uid=10001,gid=10001
podman run -d --pod scrap-pod --name scrap-pod-app \
    -v $base/data:/data:z -e SCRAP_DATA_DIR=/data --env-file $base/scrap.env \
    localhost/scrap:dev serve --host 127.0.0.1 --port 8000
podman run -d --pod scrap-pod --name scrap-pod-ts --user 10001:10001 \
    -v $base/tailscale:/var/lib/tailscale:z \
    --entrypoint tailscaled docker.io/tailscale/tailscale:stable \
    --tun=userspace-networking --statedir=/var/lib/tailscale --socket=/tmp/tailscaled.sock

  • --userns=keep-id:uid=10001,gid=10001 maps scrap’s user in the image, 10001, to you, so the files under $base/data stay yours. Podman takes it only on the pod, not on a container in one.

  • :z relabels each folder so that a container can write to it with SELinux enforcing.

  • There is no memory cap: on cgroups v1, as on DLS workstations, rootless podman ignores --memory.

  • --user 10001:10001 runs tailscaled as you. Containers in this pod run as 10001 anyway, but the page says so because it matters: see “Why Tailscale does not run as root in its container” above.

  • --socket=/tmp/tailscaled.sock puts tailscaled’s control socket where user 10001 can create it; the default, under /var/run/tailscale, needs root.

  • --entrypoint tailscaled skips the image’s own start-up script, which gives up and exits if you have not logged in within about 40 seconds.

Check that scrap answers inside the pod and not on the workstation:

podman exec scrap-pod-ts wget -qO- http://127.0.0.1:8000/healthz
curl http://127.0.0.1:8000/healthz

The first should print {"status":"ok",...}; the second should fail with Connection refused. If scrap is not running, see podman logs scrap-pod-app and Troubleshooting.

Join your tailnet and publish scrap#

Every tailscale command must name that socket, so define a shell function for them (again in each new shell, like $base):

ts() { podman exec scrap-pod-ts tailscale --socket=/tmp/tailscaled.sock "$@"; }

Log in, with a terminal attached so that you can watch it:

podman exec -it scrap-pod-ts tailscale --socket=/tmp/tailscaled.sock up --hostname=scrap

This prints a login URL and waits: open it in any browser and log in to your new tailnet. (To join without a browser, make an auth key in the admin console and pass --auth-key=<key> instead.) Then publish scrap with Tailscale Serve on the standard HTTPS port:

ts serve --bg --https=443 http://127.0.0.1:8000
ts serve status

--bg keeps the setting, in Tailscale’s state on /scratch, across restarts. serve status prints the address. If it is not https://scrap.<tailnet>.ts.net (Tailscale adds a suffix if the name is taken), put the real one in $base/scrap.env and recreate scrap’s container (Update or change settings). Where UDP is blocked, Tailscale falls back to its DERP relays over HTTPS on port 443: slower, but it works.

Check it from another device#

The workstation itself is not on your tailnet (only the pod is), so check from your phone or another tailnet device instead: with Tailscale connected, open https://scrap.<tailnet>.ts.net/healthz, which should show {"status":"ok",...}. The first request can take a few seconds while Tailscale fetches the certificate. For the same reason, run Claude Code on another device on your tailnet, not on the workstation.

Open it on your phone#

With the Tailscale app connected, open https://scrap.<tailnet>.ts.net on your phone and install the app: see Capture from your phone (the PWA). Captures made while the workstation is off, or the pod stopped, wait in the app’s offline queue and are sent when it is back.

To let Claude Code sessions on another tailnet device search and write scrap, see Connect a Claude Code session; SCRAP_PUBLIC_URL is already set.

Logs#

The user journal is not available to users on DLS workstations, so journalctl --user shows nothing. Each container keeps its own output:

podman logs scrap-pod-app
podman logs scrap-pod-ts
ts status

Under systemd (Optional: start it at boot with systemd), a container is removed when its unit stops, and its logs go with it.

Optional: ingest on your Claude seat#

Photos are queued but not sent to Claude until you turn ingest on. On a Claude Team or Enterprise seat it runs through Claude Code with a long-lived token (ADR 0021). First check with your organisation’s Claude admin that unattended use of your seat is allowed. The token can use your whole seat, and calls count against your seat’s usage limits.

  1. On any machine with Claude Code logged in to your seat, run claude setup-token and copy the token it prints.

  2. From the clone, build the image with the CLI added:

    podman build -f Dockerfile.claude --build-arg BASE=localhost/scrap:dev \
    -t localhost/scrap-claude:dev .

    Rebuild this image whenever you rebuild localhost/scrap:dev, or scrap keeps running the old one.

  3. Add to $base/scrap.env, which stays mode 600 on /scratch (never put the token in your NFS home):

    SCRAP_INGEST=on
SCRAP_LLM_BACKEND=cli
CLAUDE_CODE_OAUTH_TOKEN=<your token>

    podman inspect scrap-pod-app shows the container’s environment, token included, in plain text: do not paste its output anywhere.

  4. Recreate scrap’s container as in Update or change settings, with localhost/scrap-claude:dev in place of localhost/scrap:dev (under systemd, regenerate the units).

What the token gives away, the budget and the limits are in the how-to’s “On a Claude seat, with no API key”, under Ingest settings. An API key works instead: it comes from a Claude Console account, which is separate from a seat and billed per use.

Update or change settings#

Podman reads --env-file only when it creates a container, so after changing $base/scrap.env, or to run a newly built image, remove scrap’s container and run it again:

podman rm -f scrap-pod-app
podman run -d --pod scrap-pod --name scrap-pod-app \
    -v $base/data:/data:z -e SCRAP_DATA_DIR=/data --env-file $base/scrap.env \
    localhost/scrap:dev serve --host 127.0.0.1 --port 8000

Back up first if the new image may change the database: see Database changes and rolling back. To update Tailscale, podman pull its image, then remove and run scrap-pod-ts the same way. Its login and Serve setting are kept on /scratch.

Under systemd (Optional: start it at boot with systemd), do not remove containers by hand. The units create each container afresh at every start, reading $base/scrap.env again and running whatever localhost/scrap:dev (or Tailscale’s pulled image) now is, so after a settings change or a rebuild, restart the container’s unit:

systemctl --user restart container-scrap-pod-app.service

(container-scrap-pod-ts.service for Tailscale.) To change a container’s command line, such as switching to localhost/scrap-claude:dev, regenerate the units as described there.

Start it again#

The pod does not start by itself, and it stops when you log out: unless your account lingers, systemd stops all your processes when your last session ends. After a reboot, a logout or podman pod stop:

podman pod start scrap-pod

To keep the pod running after you log out, run loginctl enable-linger (if it is refused, see below). That alone keeps a pod you started by hand alive; to start it at boot too, follow Optional: start it at boot with systemd.

Optional: start it at boot with systemd#

Warning

Not yet run end to end at DLS. The generated units have been checked with systemd-analyze --user verify on a DLS workstation, but not enabled there.

Podman 4.9 has no Quadlet .pod units, so generate systemd user units from the running pod instead; podman generate systemd prints a DEPRECATED notice recommending Quadlet, which you can ignore here. The units record each container’s command line, so the pod must be running as above. Each unit gets a guard so that it runs only on this workstation, not on another machine that mounts your NFS home:

mkdir -p ~/.config/systemd/user
cd ~/.config/systemd/user
podman generate systemd --new --files --name scrap-pod
for u in pod-scrap-pod container-scrap-pod-app container-scrap-pod-ts; do
    mkdir -p $u.service.d
    printf '[Unit]\nConditionPathIsDirectory=/scratch/%s/scrap-pod\n' "$USER" \
        >$u.service.d/host.conf
done
systemd-analyze --user verify pod-scrap-pod.service

With --new, systemd creates the pod and containers afresh at each start and removes them at each stop, and restarts a container that fails. Stop and remove the ones you made by hand, then start the pod’s unit:

podman pod stop scrap-pod
podman pod rm scrap-pod
systemctl --user daemon-reload
systemctl --user enable --now pod-scrap-pod.service
loginctl enable-linger

enable-linger lets your user services run when you are not logged in, and start at boot. If it is refused, ask IT to run sudo loginctl enable-linger <fedid> for you. To change a container’s command line later, first systemctl --user disable --now pod-scrap-pod.service, then make the pod by hand again as above and regenerate the units.

Back up#

deploy/install.sh and its units are not used here: its scrap.service would start a second scrap. Its daily backup and nightly gc timers have no equivalent for the pod yet; until then, back up by hand. A backup is safe while scrap runs:

stamp=$(date -u +%Y%m%dT%H%M%SZ)
podman run --rm --userns=keep-id:uid=10001,gid=10001 --network=none \
    -v $base/data:/data:z -v $base/backups:/backups:z -e SCRAP_DATA_DIR=/data \
    localhost/scrap:dev backup /backups/$stamp

Old backups are not deleted for you. /scratch is not backed up either, and the backups are on the same disk as the data: copy $base/backups somewhere else if what you put in scrap matters. To restore, see Restore.

Stop or remove it#

To stop scrap and Tailscale, podman pod stop scrap-pod (or, under systemd, systemctl --user stop pod-scrap-pod.service); start them again as above.

To remove them, do these steps in order. If you set up systemd, the pod must be running under it for the first step, and the second uses systemctl instead of podman pod.

  1. While the pod is up, take it off your tailnet:

    ts serve reset
ts logout

  2. Stop and remove the pod:

    podman pod stop scrap-pod
podman pod rm scrap-pod

    Under systemd, run systemctl --user disable --now pod-scrap-pod.service instead, remove the *scrap-pod* files and folders from ~/.config/systemd/user, and run systemctl --user daemon-reload.

  3. Remove Tailscale’s state:

    rm -r /scratch/$USER/scrap-pod/tailscale

    If that state was made by an older version of this page, which ran Tailscale as root in its container, some files are not yours: use podman unshare rm -r instead.

Then delete the machine under Machines in the Tailscale admin console, if it is still listed.

Your data in /scratch/$USER/scrap-pod stays until you delete it.
